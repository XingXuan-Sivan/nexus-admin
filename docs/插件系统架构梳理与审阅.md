# 插件系统架构梳理与审阅

> **文档目的**：基于项目实际代码，对 Nexus Admin 插件化业务拓展平台的插件系统进行完整梳理，  
> 供架构、设计、代码审阅使用。**本文档不修改任何项目实际代码。**

---

## 1. 系统概览与架构总图

### 1.1 项目定位

Nexus Admin 是一个基于 **Spring Boot 3.2 + 微内核架构** 的插件化业务拓展平台。平台核心由三类模块构成：

```text
nexus-admin-core     → 插件运行时核心（纯 Java，无 Spring 依赖）
nexus-admin-api      → API 层 + 扩展点定义 + 默认 Web 能力
nexus-admin-app      → Spring Boot 宿主应用，桥接 core/api 到 Spring 容器
```

插件则位于独立的 `plugins/` 目录下，拥有独立的类加载器和生命周期。

### 1.2 整体架构

```text
┌─────────────────────────────────────────────────────────────────┐
│                     nexus-admin-app (宿主应用)                    │
│  ┌───────────┐  ┌──────────────┐  ┌────────────────────────┐    │
│  │Bootstrap  │  │ Spring MVC   │  │  插件静态资源托管       │    │
│  │ Config    │  │ Controllers  │  │  /plugins/{id}/assets    │    │
│  └───────────┘  └──────────────┘  └────────────────────────┘    │
├─────────────────────────────────────────────────────────────────┤
│                     nexus-admin-api (API层)                      │
│  ┌───────────┐  ┌──────────────┐  ┌────────────────────────┐    │
│  │ 管理面板   │  │  UI 贡献     │  │  扩展点定义 (SPI)       │    │
│  │ REST API  │  │  注册表      │  │  PermissionResolver等   │    │
│  └───────────┘  └──────────────┘  └────────────────────────┘    │
├─────────────────────────────────────────────────────────────────┤
│                    nexus-admin-core (核心层)                      │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────────┐   │
│  │ Plugin   │ │Extension │ │  Event   │ │  Config          │   │

│        │                                                         │
│  ┌─────┴─────────────────────────────────────────────────┐      │
│  │  插件发现 → 解析 → 加载 → 初始化 → 启动 → 运行               │      │

```

### 1.3 核心设计原则

| 原则 | 说明 |
|------|------|
| **微内核架构** | core 模块不依赖 Spring，仅提供纯接口和默认实现 |
| **Facade 门面模式** | 四大门面（Plugin/Extension/EventBus/Config）聚合底层能力 |
| **拓展点驱动** | 所有可替换能力通过 `ExtensionPoint` + `ExtensionRegistry` 实现 |
| **声明式配置** | 插件通过 `plugin.json` 声明元数据，无需编程注册 |
| **生命周期状态机** | 严格的 11 态状态机控制插件流转 |
| **模块单向依赖** | core ← api ← app，core 不感知 HTTP/Web 层 |

## 2. 模块职责与依赖关系

### 2.1 模块职责

| 模块 | 职责 | 依赖 |
|------|------|------|
| **nexus-admin-core** | 插件运行时：生命周期管理、扩展注册、事件总线、配置中心 | 无（纯 Java，仅依赖 SLF4J） |
| **nexus-admin-api** | API 层：REST Controller、Service、领域模型、API 级扩展点、响应体系 | core |
| **nexus-admin-app** | Spring Boot 宿主：Bean 装配、启动引导、静态资源托管 | core, api |
| **plugins/demo-plugin** | 示例插件 | core |
| **plugins/system-user-plugin** | 用户管理插件：Controller + Service + Mapper | core, api |

### 2.2 依赖方向

```text
core  ←  api  ←  app
 ↑        ↑
 └── plugins（仅依赖 core，或同时依赖 core + api）
```

## 3. 插件生命周期详解

### 3.1 状态机（11 种状态）

```text
                   ┌─────────┐
                   │DISCOVERED│ ← 插件被扫描发现，仅有元数据
                   └────┬─────┘
                        │ resolve()
                   ┌────▼─────┐
                   │ RESOLVED │ ← 依赖解析、版本校验完成
                   └────┬─────┘
                        │ load() + register schema
                   ┌────▼─────┐
                   │  LOADED  │ ← 类加载完成
                   └────┬─────┘
                        │ onInitialize()
                   ┌────▼──────┐
                   │INITIALIZED│ ← 插件初始化回调已执行
                   └────┬──────┘
              ┌─────────┼─────────┐
              │ enable()│         │ disable()
         ┌────▼─────┐   │    ┌────▼─────┐
         │ STARTING │   │    │ DISABLED │ ← 被禁用，不可运行
         └────┬─────┘   │    └────┬─────┘
              │ onStart()│         │ enable()
         ┌────▼─────┐   │         │
         │  ACTIVE  │◄──┘         │
         └────┬─────┘             │
              │ stop()            │
         ┌────▼─────┐             │
         │ STOPPING │             │
         └────┬─────┘             │
              │ onStop()          │
         ┌────▼─────┐             │
         │ STOPPED  │─────────────┘
         └────┬─────┘
              │ unload()
         ┌────▼─────┐
         │ UNLOADED │ ← 终态，类加载器已释放
         └──────────┘

  所有状态在异常时均可迁移到 ──► FAILED ──► UNLOADED
  ACTIVE 状态下支持热升级 ──► UPGRADING ──► ACTIVE
```

### 3.2 完整启动流程（bootstrap）

```text
bootstrap()
    │
    ├── 1. discover()     扫描插件源 → 生成 PluginMetadata 列表
    │      └── PluginDiscoverer → sources → finders → parsers
    │
    ├── 2. resolve()      依赖校验 + 拓扑排序
    │      └── PluginResolver → VersionManager + DependenceManager
    │
    ├── 3. load()         类加载 + 注册 Schema
    │      └── PluginLoader.load(metadata) → PluginWrapper
    │      └── ConfigManager.registerPlugin(pluginId, classLoader)
    │      └── PluginRegistry.register(wrapper)
    │
    ├── 4. initialize()   调用 plugin.onInitialize(context)
    │      └── 创建 PluginContext（四层模型）
    │
    └── 5. autoStartIfNecessary()
           └── 检查 autoStart 配置和 disabled 列表
           └── 调用 start(pluginId) → onStart(context)
```

## 6. UI 贡献机制详解

### 6.1 数据流

```text
plugin.json → PluginDescriptorParser 解析 → PluginDescriptor.contributes()
                                                    │
                                    插件 LOADED 状态时即静态可用
                                                    │
                                    前端 GET /admin/v1/ui/manifest
                                                    │
                                    UIController → UIContributionRegistryImpl
                                                    │
                                    遍历 ACTIVE 插件 → 聚合 contributes
                                                    │
                                    返回 Map<pluginId, PluginContributes>
                                                    │
                                    前端渲染菜单/注册路由/填充挂载点
```

### 6.2 API 端点

| 端点 | 方法 | 说明 |
|------|------|------|
| `/admin/v1/ui/manifest` | GET | 所有活跃插件的完整 contributes 映射 |
| `/admin/v1/ui/menus` | GET | 聚合排序后的菜单列表 |
| `/admin/v1/ui/routes` | GET | 聚合后的路由列表 |
| `/plugins/{pluginId}/assets/**` | GET | 插件静态资源（HTML/JS/CSS），从 ClassLoader 加载 |

### 6.3 静态资源托管安全措施

1. **目录限制**：仅允许 `static/` 下的资源
2. **路径遍历防护**：禁止 `..`、绝对路径、反斜杠
3. **插件状态校验**：仅 ACTIVE 状态的插件可访问
4. **MIME 限制**：仅允许常见 Web 资源类型（最多 5MB）
5. **缓存策略**：`Cache-Control: public, max-age=3600`

## 7. 扩展点/SPI 体系

### 7.1 核心机制

```text
ExtensionPoint (标记接口)
    ↑
    所有 SPI 接口继承
    │
    ├── PermissionResolver     (api.extension.permission)
    ├── WebEndpointExtension   (api.extension.web)
    ├── AuthProvider           (api.extension.auth)
    ├── AuthChallengeHandler   (api.extension.auth)
    └── ... 其他扩展点
            │
            ▼
ExtensionRegistry (注册中心)
    ├── register(pointType, implementation, priority)
    ├── get(pointType) → Optional<T>  (最高优先级)
    ├── getAll(pointType) → List<T>   (优先级降序)
    └── unregisterByPluginId(pluginId) (生命周期联动)
            │
            ▼
ExtensionConsumer<T> (消费者模板)
    ├── 缓存 + 事件驱动失效
    └── 监听 ExtensionChangedEvent 自动刷新
```

### 7.2 关键扩展点清单

| 扩展点 | 所在模块 | 作用 |
|--------|----------|------|
| `PermissionResolver` | api | 权限解析与决策 |
| `WebEndpointExtension` | api | 插件 Web 端点注册/卸载 |
| `AuthProvider` | api | 认证提供者 |
| `AuthChallengeHandler` | api | 认证挑战处理 |
| `UIContributionRegistry` | api | UI 贡献聚合（接口在 api，默认实在 api） |

## 11. 系统审阅与总结

### 11.1 架构优点

| 优点 | 说明 |
|------|------|
| **微内核设计清晰** | core 模块纯 Java 无 Spring 依赖，职责边界清晰 |
| **Facade 模式运用得当** | 四大 Facade 解耦了 PluginManager 与底层组件的直接依赖 |
| **生命周期状态机严谨** | 11 态 + 状态迁移映射表，线程安全且可扩展 |
| **四层上下文模型** | PluginContext 聚合 Info/Runtime/Workspace/Platform，禁止直接获取 PluginManager |
| **声明式 contributes** | 借鉴 VS Code，插件通过 JSON 声明 UI 能力，静态可分析 |
| **扩展点缓存机制** | ExtensionConsumer 实现缓存 + 事件驱动失效，减少注册中心查询 |
| **安全防护到位** | 静态资源托管有路径遍历防护、状态校验、MIME 限制 |
| **Bean 可替换性** | @ConditionalOnMissingBean 保护所有组件，支持插件覆盖 |

### 11.2 潜在改进点

| 问题 | 严重度 | 建议 |
|------|--------|------|
| **AbstractPlugin 模板方法为 final** | 中 | 当前设计 `onStart/onStop` 为 final，子类只能覆写无参 `start()/stop()`。这使得某些特殊场景（如需要在 onStart 前后执行通用逻辑）不灵活。权衡：保证了上下文安全，但牺牲了灵活性 |
| **Schema 格式不统一** | 低 | core 自身平台 Schema 仍使用 YAML 格式（platform.yml），而插件 Schema 已迁移到 JSON Schema。建议统一 |
| **contributes 中 pluginId 未携带** | 中 | 实际代码中 `PluginContributes.MenuContribution` 等 Record 不包含 pluginId 字段，前端聚合后不易区分来源。设计文档中的 API 响应示例包含了 pluginId，但实际代码未携带。建议在 Record 中添加 |
| **版本升级功能未实现** | 低 | upgradeCold/upgradeHot 抛 UnsupportedOperationException，属远期规划 |
| **热加载未支持** | 低 | 当前为全量加载模式，无运行时新增/热替换插件能力 |
| **插件间通信缺乏标准机制** | 中 | 当前仅通过 EventBus 实现松耦合通信，缺少同步的服务调用机制（如 OSGi Service Registry）。PlatformServices 已预留但未广泛使用 |
| **Bridge SDK 未独立发布** | 中 | window.NexusAdmin 在当前代码中未找到独立实现，iframe 通信的 Bridge SDK 有待落地 |

### 11.3 与设计文档的差异对照

| 设计文档描述 | 实际代码状态 | 差异说明 |
|-------------|-------------|----------|
| ADR-005 中 PermissionResolver 定义 `hasPermission(userId, permission): boolean` | 实际定义为 `PermissionCheck` Record + `PermissionDecision` Record | 实际代码更完善，支持 resource/action 二维权限模型 |
| ADR-005 中 Manifest API 响应含 pluginId | `PluginContributes` Record 不含 pluginId | 需要在聚合层手动添加 |
| ADR-005 中 route.path 以 `/plugins/{pluginId}/` 为前缀 | demo-plugin 使用 `/demo`（未遵循） | demo 示例需要更新以符合规范 |
| 设计文档描述 mountPoints 字段名为 `slot` | 实际代码 Record 字段名为 `target` | 命名不一致 |
| 设计文档中 `menus` 使用 `path` 字段 | 实际代码 Record 字段名为 `route` | 命名不一致 |

### 11.4 总结

Nexus Admin 的插件系统设计遵循了 **微内核 + 声明式** 的架构理念，整体架构清晰，分层合理：

1. **core 模块** 提供了完整的插件运行时基础设施：生命周期管理、扩展注册、事件总线、配置中心，且不依赖任何 DI 容器，可独立使用。
2. **api 模块** 在 core 之上构建了 Web 层能力：REST API、UI 贡献聚合、权限拦截、OpenAPI 文档等。
3. **app 模块** 通过 Spring Boot 自动装配将两者桥接，提供开箱即用的管理面板。
4. **插件系统** 通过 `plugin.json` 声明式配置实现零代码侵入的 UI 扩展，通过 ExtensionPoint 体系实现能力的可替换性。

当前系统已具备完整的插件生命周期管理、UI 贡献聚合、静态资源托管等核心能力，是一个设计良好、可落地的插件化架构。建议在后续迭代中重点关注：Bridge SDK 落地、版本升级能力、插件间通信标准化、Schema 格式统一等方向。
