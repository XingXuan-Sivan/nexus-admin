## 议题一：API 分区、版本化与命名空间策略

### 涉及包与类

| 类 | 包路径 | 作用 |
|---|---|---|
| `PluginManageController` | `com.nexusadmin.api.controller` | 插件管理 API，映射 `/admin/v1/plugins` |
| `ConfigController` | `com.nexusadmin.api.controller` | 配置管理 API，映射 `/admin/v1/config` |
| `SystemStatusController` | `com.nexusadmin.api.controller` | 系统状态 API，映射 `/admin/v1/system` |
| `UIController` | `com.nexusadmin.api.controller` | UI 元数据 API，映射 `/admin/v1/ui` |
| `AuthController` | `com.nexusadmin.api.controller` | 认证 API，映射 `/admin/v1/auth` |
| `UserController` | `com.nexusadmin.api.controller` | 用户管理 API，映射 `/admin/v1/users` |
| `RoleController` | `com.nexusadmin.api.controller` | 角色管理 API，映射 `/admin/v1/roles` |
| `PermissionController` | `com.nexusadmin.api.controller` | 权限管理 API，映射 `/admin/v1/permissions` |
| `AuthFilter` | `com.nexusadmin.api.auth` | 拦截 `/admin/**`（基于 PanelWebProperties.basePath），执行认证检查 |

### 实际代码与设计对照

**ADR-005 设计：**

```text
/admin/v1/
  ├── plugins/**     → 插件生命周期管理
  ├── config/**      → 配置中心管理
  ├── system/**      → 系统状态与平台信息
  ├── ui/**          → UI元数据
  ├── auth/**        → 认证端点
  ├── users/**       → 核心业务对象
  └── roles/**       → 核心业务对象
```

**实际实现（完全一致，且超额完成）：**

```text
/admin/v1/
  ├── plugins/**     → PluginManageController        ✅
  ├── config/**      → ConfigController              ✅
  ├── system/**      → SystemStatusController         ✅
  ├── ui/**          → UIController                   ✅
  ├── auth/**        → AuthController                 ✅
  ├── users/**       → UserController                 ✅
  ├── roles/**       → RoleController                 ✅
  └── permissions/** → PermissionController           ✅ (设计外新增)
```

**路径引用更新情况：**

- `PluginManageController`：`@RequestMapping("/admin/v1/plugins")` — 已按决策更新 ✅
- `AuthFilter` 基于 `PanelWebProperties.basePath`（默认 `/admin`）拦截，不感知版本号 ✅
- `PermissionInterceptor` 基于 `PanelWebProperties.basePath + "/**"` 拦截 ✅

### 审阅意见

- **优点**：所有 Controller 统一使用 `/admin/v1/` 前缀，与设计完全对齐。`PermissionController` 的加入合理填补了权限管理的 API 空白
- **关注点**：设计文档中的 `/admin/v1/system/endpoints` 尚未实现（ADR-005 已标记为可选）；对于未来浏览器直接访问 `/admin/` 根路径，建议在前端做一次永久重定向到 `/admin/v1/`

| ADR-005: `menus[].parent` = `"root"` 表示顶级 | 代码: `parentId`（空字符串表示顶级） | 字段名不同，默认值语义不同 |
| ADR-005: `menus[].path` | 代码: `menus[].route` | 字段名从 `path` 改为 `route`，与路由级 `path` 区分 |

- **优点**：`PluginContributes` 使用 Java Record + compact constructor 实现了不可变模型，null-safe 处理完善。`EMPTY` 常量保证了向后兼容
- **优点**：`UIContributionRegistryImpl` 仅遍历 ACTIVE 状态插件，避免未启动插件的 UI 污染
- **关注点**：`UIController` 缺少 `/admin/v1/ui/mountPoints` 端点，挂载点贡献目前只能通过 `/manifest` 获取；`getRoutes()` 未按 order 排序

## 议题四：认证 Token 管理与权限可拓展模型

### 涉及包与类

| 类 | 包路径 | 作用 |
|---|---|---|
| `AuthController` | `com.nexusadmin.api.controller` | Token 端点（登录/登出/刷新/当前用户） |
| `AuthFilter` | `com.nexusadmin.api.auth` | 拦截 /admin/v1/** 执行认证 |
| `RequirePermission` | `com.nexusadmin.api.auth` | 权限声明注解 |
| `PermissionInterceptor` | `com.nexusadmin.api.interceptor` | 拦截器，处理 @RequirePermission 校验 |
| `PermissionResolver` | `com.nexusadmin.api.extension.permission` | 权限解析与决策扩展点 |
| `PermissionResolver.PermissionCheck` | 同上（内嵌 Record） | 权限检查请求（userId/resource/action/attributes） |
| `PermissionResolver.PermissionDecision` | 同上（内嵌 Record） | 授权决策（allowed/reason/permissionCodes） |
| `CompositeAuthProvider` | `com.nexusadmin.api.auth` | 组合认证提供者 |
| `BootstrapAuthProvider` | `com.nexusadmin.api.auth` | 默认兜底认证实现，支持 Bearer Token 验证 |
| `LoginRequest` | `com.nexusadmin.api.domain.identity` | 登录请求体 |
| `TokenResponse` | `com.nexusadmin.api.domain.identity` | Token 响应（accessToken/refreshToken/expiresIn） |
| `RefreshRequest` | `com.nexusadmin.api.domain.identity` | 刷新请求体 |
| `CurrentUserInfo` | `com.nexusadmin.api.domain.identity` | 当前用户信息 |
| `UserController` | `com.nexusadmin.api.controller` | 用户 CRUD API |
| `RoleController` | `com.nexusadmin.api.controller` | 角色 CRUD API |
| `PermissionController` | `com.nexusadmin.api.controller` | 权限查询 API |

### 认证流程对比

**ADR-005 设计流程：**

```text
请求进入 → AuthFilter 拦截
  → 解析 Token 获取 userId
  → 检查目标方法是否标注 @RequirePermission
  → 委托 PermissionResolver.hasPermission(userId, permission)
  → 通过则放行，拒绝则返回 403
```

**实际代码实现流程：**

```text
请求进入 → AuthFilter 拦截 (只拦截 /admin/**，不感知版本号)
  → 公开端点（由 PanelWebProperties.publicEndpoints 配置，AntPathMatcher 匹配）→ 放行
  → Session/BearerToken/Basic 三级认证
  → 认证通过后存入 Session（通过 HttpAuthUtils 工具类）
  → chain.doFilter() 放行给 Spring MVC
  → 认证失败委托 AuthChallengeHandler（默认返回 401）
───────────────────────────────────────
  → PermissionInterceptor.preHandle()
    → 解析 @RequirePermission 注解
    → 值为 "*" → 仅检查是否已认证（通过 HttpAuthUtils.getSessionUser()）
    → 值为具体权限 → 委托 PermissionResolver.decide()
    → 使用 PermissionCheck/PermissionDecision 模型
    → 拒绝返回 403（RFC 7807 ProblemDetail 格式）
```

**关键差异：** ADR-005 设计为 `AuthFilter` 内部执行权限检查，但实际代码中认证与授权分离——`AuthFilter` 只负责认证，`PermissionInterceptor` 负责授权。这种分离更符合单一职责原则，是更优的设计。此外，`AuthFilter` 已移除表单登录支持，并通过 `PanelWebProperties` 实现路径可配置化，通用 Token/Session 操作收敛至 `HttpAuthUtils` 工具类消除重复代码。

### `@RequirePermission` 使用统计

| Controller | 使用的方法数 | 权限标识示例 |
|---|---|---|
| `PluginManageController` | 7 个方法 | `plugins.view`、`plugins.manage` |
| `AuthController` | 2 个方法 | `*`（仅需认证） |
| `ConfigController` | 6 个方法 | `config.view`、`config.manage` |
| `SystemStatusController` | 2 个方法 | `system.view` |
| `UIController` | 3 个方法 | `*`（仅需认证） |
| `UserController` | 5 个方法 | `users.view`、`users.manage` |
| `RoleController` | 5 个方法 | `roles.view`、`roles.manage` |
| `PermissionController` | 2 个方法 | `permissions.view` |

### 设计与代码差异对照

| 设计文档内容 | 实际代码 | 差异 |
|---|---|---|
| ADR-005: `PermissionResolver.hasPermission(userId, permission)` 返回 boolean | 代码: `decide(PermissionCheck, context)` 返回 `PermissionDecision` | 代码模型更丰富（含 reason、permissionCodes 及扩展属性 map） |
| ADR-005: `PermissionResolver.resolvePermissions(userId)` 返回 `List<String>` | 代码: `resolvePermissions(userId, context)` 返回 `Set<Permission>` | 返回类型从 `List<String>` 增强为 `Set<Permission>` 对象集合 |
| ADR-005: 权限在 AuthFilter 中检查 | 代码: 权限在 PermissionInterceptor 中检查 | 认证/授权分离，架构更清晰 |

### 审阅意见

- **优点**：认证（AuthFilter）与授权（PermissionInterceptor）分离，职责清晰
- **优点**：`AuthFilter` 基于 `PanelWebProperties.basePath` 拦截 `/admin/**`，不感知版本号，新增 API 版本无需修改过滤器配置
- **优点**：公开端点通过 `PanelWebProperties.publicEndpoints` 配置，使用 `AntPathMatcher` 匹配，支持 yml 动态扩展
- **优点**：Token/Session 操作统一收敛至 `HttpAuthUtils` 工具类，消除 `AuthFilter`、`AuthController`、`PermissionInterceptor` 中的重复代码
- **优点**：`PermissionResolver` 的 `PermissionCheck`（含 resource/action/attributes）比设计中的简单 `hasPermission(userId, permission)` 更具表达力，支持 ABAC 风格的属性级决策
- **优点**：`*` 通配符设计让仅需认证的端点（如 UI 元数据、登出、当前用户）无需分配具体权限，降低了使用门槛
- **优点**：`PermissionInterceptor` 在 `PermissionResolver` 未注册时默认放行，与 ADR-005 风险缓解策略一致
- **修复**：`BootstrapAuthProvider` 已覆写 `validateToken()`，与 `login()` 生成的 `"token-{userId}"` 格式 Token 配套验证，确保 Bearer Token 认证流程完整可用
- **修复**：`DefaultAuthChallengeHandler` 已移除 `WWW-Authenticate: Basic` 响应头，避免触发浏览器原生 Basic 认证弹窗
- **关注点**：`UserService` 和 `RoleService` 的 CRUD 实现可能是骨架，取决于具体插件覆盖。`PermissionService.list()` 和 `tree()` 直接抛出 UnsupportedOperationException

## 议题五：统一响应体系与查询规范

### 涉及包与类

| 类 | 包路径 | 作用 |
|---|---|---|
| `Result` | `com.nexusadmin.api.domain.result` | 成功响应基类（code + message） |
| `DataResult<T>` | `com.nexusadmin.api.domain.result` | 带数据载荷的成功响应 |
| `PageResult<T>` | `com.nexusadmin.api.domain.result` | 分页成功响应（total/page/size/items） |
| `ProblemDetail` | `com.nexusadmin.api.domain.result` | RFC 7807 错误响应 |
| `ProblemDetail.FieldError` | 同上（内嵌类） | 字段级校验错误 |
| `StatusCode` | `com.nexusadmin.api.domain.result` | 状态码接口契约 |
| `StatusCodes` | `com.nexusadmin.api.domain.result` | 通用状态码枚举（按模块分段） |
| `GlobalExceptionHandler` | `com.nexusadmin.api.exception` | 全局异常 → ProblemDetail 转换 |

### 响应体体系对照

**ADR-005 设计：**

```text
成功响应（Content-Type: application/json）
  Result → code + message
  DataResult<T> → code + message + data
  PageResult<T> → code + message + total + page + size + items

错误响应（Content-Type: application/problem+json）
  RFC 7807 Problem Details → type + title + status + detail + instance
    扩展: errorCode + fieldErrors[]
```

**实际实现（完全一致）：**

- `Result` / `DataResult` / `PageResult` 均提供静态工厂方法和 Builder 模式 ✅
- `ProblemDetail` 严格遵循 RFC 7807 标准字段 + `errorCode`/`fieldErrors` 扩展 ✅
- `GlobalExceptionHandler` 返回 `Content-Type: application/problem+json` ✅
- `type` URI 格式 `https://nexusadmin.io/probs/{category}/{problem}` ✅

### 错误码分段对照

| ADR-005 设计 | 实际 StatusCodes 枚举 | 差异 |
|---|---|---|
| 1xxx 认证：1001-1005 | 1001-1006（新增 ACCOUNT_DISABLED） | ✅ 超额完成 |
| 2xxx 插件：2001-2005 | 2001-2006（新增 PLUGIN_ALREADY_EXISTS） | ✅ 超额完成 |
| 3xxx 配置：3001-3004 | 3001-3005（新增 CONFIG_READ_ONLY） | ✅ 超额完成 |
| 4xxx 系统：4001-4002 | 4001-4002 | ✅ 完全一致 |
| 5xxx 业务：5001-5003 | 5001-5004（新增 ROLE_ALREADY_EXISTS） | ✅ 超额完成 |

### 分页查询参数规范

ADR-005 定义的统一查询参数（`page`/`size`/`sort`/`filter`）在实际代码中：

- `UserController.list()` 和 `RoleController.list()` 使用 `@RequestParam(defaultValue = "1") int page` 和 `@RequestParam(defaultValue = "20") int size` ✅
- 返回 `PageResult<T>` ✅
- `sort` 和 `filter` 参数尚未在任何 Controller 中使用（需求驱动，合理）

### GlobalExceptionHandler 异常分级

Handler 按优先级处理 8 类异常，全部转为 RFC 7807 格式：

```
PluginOperationException  → 409 plugin/operation-failed    (2xxx errorCode)
PluginLoadException       → 500 plugin/load-failed         (2004)
PluginDescriptorException → 400 plugin/descriptor-invalid  (2005)
DescriptorParseException  → 400 plugin/descriptor-invalid  (2005)
PluginSourceException     → 500 plugin/source-error        (2004)
ExtensionNotFoundException → 404 system/extension-not-found (4001)
DomainException           → 422 business/domain-violation  (400)
PluginException           → 500 plugin/error               (2004)
CoreException             → 500 system/core-error          (500)
IllegalArgumentException  → 400 request/invalid-argument   (400)
MethodArgumentNotValidException → 400 request/validation-failed (含 fieldErrors)
AccessDeniedException     → 403 auth/access-denied         (1004)
Exception (兜底)          → 500 system/internal-error      (500)
```

### 审阅意见

- **优点**：响应体系实现与设计完全对齐且超额完成。RFC 7807 的 `type` URI、`title`、`status`、`detail`、`instance` 标准字段全部到位
- **优点**：`GlobalExceptionHandler` 异常覆盖全面，从插件操作到参数校验到通用异常均有对应 Handler，且 `MethodArgumentNotValidException` 正确提取了 `fieldErrors`
- **优点**：`PageResult` 的 Builder 模式与 `Result`/`DataResult` 风格一致
- **优点**：错误码分段比设计更丰富（每个分段都新增了实际需要的码值）
- **关注点**：`UserController` 和 `RoleController` 使用了 `PageResult`，但 `PluginManageController.listAll()` 仍返回 `DataResult<List>`（未分页）。插件数量增长后可能需要改成分页

## 议题六：插件前端资源接入方案

### 涉及包与类

| 类 | 包路径 | 作用 |
|---|---|---|
| `PluginStaticResourceController` | `com.nexusadmin.api.controller` | 插件静态资源托管端点 |

### 实际端点

```
GET /plugins/{pluginId}/assets/**
```

从 ACTIVE 插件的 ClassLoader 中加载 `static/` 目录下的资源文件。

### 安全措施（实际代码实现）

```java
// 路径遍历防护
path.contains("..")   → 拒绝
path.startsWith("/")  → 拒绝
path.contains("\\")   → 拒绝

// 资源大小限制
MAX_RESOURCE_SIZE = 5 * 1024 * 1024  // 5MB

// 仅允许 static/ 目录下的资源
STATIC_PREFIX = "static/"

// 插件状态检查
仅 ACTIVE 状态的插件可访问其资源

// MIME 类型白名单（19 种）
HTML/CSS/JS/JSON/PNG/JPG/GIF/SVG/ICO/WOFF/WOFF2/TTF/EOT/XML/TXT/WEBP
```

### component 路径映射

ADR-005 定义的映射规则：

```text
plugin.json: component: "system-user-plugin/pages/UserList"
    ↓
实际 URL: /plugins/system-user-plugin/assets/static/system-user-plugin/pages/UserList.html
```

注意事项：Controller 自动在 `component` 前拼接 `static/` 前缀，所以实际的 ClassLoader 资源路径是 `static/system-user-plugin/pages/UserList.html`。

### 审阅意见

- **优点**：路径遍历防护覆盖了 `..`、`/` 开头、`\` 三种常见攻击向量
- **优点**：MIME 类型白名单覆盖了前端所需的所有常见格式
- **优点**：限制 5MB 大小防止内存耗尽
- **缺失**：JS Bridge SDK（`nexus.getToken()`、`nexus.navigateTo()` 等）尚未实现。这是 ADR-005 第一阶段方案的核心组件，目前仅在设计文档中定义
- **关注点**：前端组件路径约定（`pluginId/pages/PageName` → `static/pluginId/pages/PageName.html`）目前依赖隐式 `.html` 后缀，`UIController` 返回的 `component` 不含后缀

## 总体审阅总结

### 七个议题完成度

| 议题 | 完成度 | 关键已实现 | 关键缺失 |
|---|---|---|---|
| 议题一：API分区与版本化 | **100%** | 所有 Controller 使用 /admin/v1/ 前缀 | 无 |
| 议题二：UI贡献声明 | **95%** | PluginContributes + UIContributionRegistry + UIController | mountPoints 独立端点缺失 |
| 议题三：配置Schema增强 | **60%** | schema.json + x-ui-group | x-ui-options 未使用、JSON Schema 验证未执行、getScopes/resetConfig 未实现 |
| 议题四：认证与权限 | **100%** | AuthController + RequirePermission + PermissionInterceptor + PermissionResolver + PanelWebProperties + HttpAuthUtils（已重构对齐 ADR-007） | 无（超额完成并已优化横切关注点） |
| 议题五：响应体系 | **100%** | Result/DataResult/PageResult + RFC 7807 ProblemDetail + 分段错误码 | 无（超额完成） |
| 议题六：前端资源接入 | **70%** | PluginStaticResourceController + 安全防护 | JS Bridge SDK 未实现 |
| 议题七：API发现与文档 | **90%** | Knife4j + SystemStatusController + OpenApiCustomizer | /system/endpoints 未实现（可选） |

### 架构优点

1. **认证与授权分离**：`AuthFilter` 只认证，`PermissionInterceptor` 只授权，比 ADR-005 设计文件中的合并在 AuthFilter 的方案更清晰
2. **横切关注点已优化**：`AuthFilter` 和 `PermissionInterceptor` 基于 `PanelWebProperties.basePath`（`/admin`）拦截，不感知版本号；Token/Session 操作收敛至 `HttpAuthUtils`；公开端点通过 yml 可配置
3. **RFC 7807 贯彻彻底**：从 `ProblemDetail` 模型到 `GlobalExceptionHandler` 到 `PermissionInterceptor` 的 403 响应，全部采用 `application/problem+json`
4. **PluginContributes 不可变模型**：Java Record + compact constructor 实现了编译期安全，`EMPTY` 常量保证向后兼容
5. **安全防护到位**：`PluginStaticResourceController` 的路径遍历防护、大小限制、MIME 白名单、ACTIVE 状态检查构成了多层安全防线

### 优先修复建议（按优先级）

| 优先级 | 议题 | 事项 | 影响 |
|---|---|---|---|
| P0 | 议题三 | 在 PUT 配置值时执行 JSON Schema 验证 | 无验证时非法配置值会直接写入，可能导致插件异常 |
| P1 | 议题六 | 实现 JS Bridge SDK（postMessage 通信） | 无 Bridge 则 iframe 内插件无法与主框架交互 |
| P2 | 议题三 | 实现 ConfigService.getScopes() 和 resetConfig() | 前端配置管理页面缺少配置域列表和重置功能 |
| P2 | 议题二 | UIController 增加 `/admin/v1/ui/mountPoints` 端点 | 挂载点贡献无法独立获取 |
| P3 | 议题三 | 在插件 schema.json 中使用 x-ui-options（password/color 等） | 前端无法获取渲染控件提示 |

### 4. 前端 JS app.js（议题六：JS Bridge 通信）

```javascript
// 通过 JS Bridge 与主框架通信（ADR-005 议题六定义）
const bridge = window.NexusBridge;

// 获取 Token 后调用订单 API（议题四：Bearer Token 认证）
async function fetchOrders() {
  const token = bridge ? await bridge.getToken() : null;
  const resp = await fetch('/api/order-plugin/orders', {
    headers: token ? { 'Authorization': `Bearer ${token}` } : {}
  });
  if (!resp.ok) {
    // 错误响应为 RFC 7807 ProblemDetail 格式（议题五）
    const problem = await resp.json();
    document.getElementById('status').textContent = `错误: ${problem.title}`;
    return;
  }
  // 成功响应为 DataResult 信封（议题五）
  const result = await resp.json();
  if (result.code === 200) {
    renderTable(result.data);
  }
}

function renderTable(orders) {
  const tbody = document.querySelector('#orderTable tbody');
  tbody.innerHTML = orders.map(o => `
    <tr>
      <td>${o.orderNo}</td>
      <td>${o.customer}</td>
      <td>¥${o.amount.toFixed(2)}</td>
      <td>${o.status}</td>
    </tr>
  `).join('');
}

document.getElementById('searchBtn').onclick = fetchOrders;
fetchOrders();
```
