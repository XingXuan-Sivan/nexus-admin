# ADR-001：移除infra模块

## 状态
**已接受（Accepted）**

## 决策时间
2026-01-30

## 背景与上下文（Context）

当前平台为一个**插件驱动平台（Plugin-Driven Platform）**，整体模块结构如下（决策前）：



```
backend-platform/
├─ platform-core/ # 内核 + SPI（领域与扩展点）
├─ platform-plugin/ # 插件 API + 插件运行时
├─ platform-infra/ # 基础设施与技术适配层
├─ platform-app/ # Spring Boot 启动器
└─ plugins/ # 插件实现（业务 / 系统能力）
```

平台已明确遵循以下核心设计原则：

1. **platform-core 只包含 SPI 与契约，不包含任何实现**
2. **所有 SPI 的实现都期望、且必须通过插件提供**
3. 插件加载、发现、生命周期、SPI 绑定与仲裁、运行期上下文等
   已全部由 `platform-plugin` 模块承担
4. 插件（包括系统插件）是能力的唯一实现来源
5. 平台本身正在向“插件即系统”的范式演进

在此背景下，`platform-infra` 模块的存在价值产生了根本性疑问。

---

## 问题陈述（Problem）

`platform-infra` 模块在当前架构中：

- 不再承担 SPI 的默认实现职责
- 不再承担插件运行时或宿主能力
- 仅作为一个“可能用于放置基础实现”的占位模块存在

同时，平台讨论中提出的 infra 可能用途包括：

- 为“无插件”场景提供最小启动支持
- 提供 ORM（如 MyBatis）、工具类等通用能力
- 作为“保底实现层”提升工程便利性

但这些用途与平台既定的插件驱动原则存在潜在冲突。

---

## 决策（Decision）

**决定取消 `platform-infra` 模块。**

具体决策如下：

1. **不再保留独立的 infra 模块**
2. 不引入任何“非插件形态”的 SPI 实现
3. 所有能力（包括系统级、通用技术能力）一律通过插件提供
4. 平台允许通过“系统插件（System Plugins）”的方式提供最小可运行能力

---

## 决策动机（Rationale）

### 1. infra 已失去不可替代职责

在当前架构中：

- SPI 定义 → `platform-core`
- SPI 实现 → `plugins`
- 插件运行时 / 宿主 → `platform-plugin`
- 系统启动 → `platform-app`

`platform-infra` 不再承担任何**不可替代、不可插件化**的职责，
已退化为“语义不清晰的中间层”。

继续保留 infra 将导致：

- 职责边界模糊
- 团队误将实现塞入 infra
- 插件优先级被逐步侵蚀

---

### 2. “保底实现”与插件驱动范式冲突

若 infra 提供：

- 用户系统默认实现
- 权限系统默认实现
- ORM / 数据访问默认实现

则会直接导致：

- SPI 不再“必须通过插件实现”
- 插件从“一等公民”退化为“可选增强”
- 平台从“插件即系统”回退为“系统 + 插件”

这是一次**不可逆的架构倒退**。

---

### 3. 通用技术能力更适合作为“系统插件”

ORM、工具类、AI 运行时、数据访问等能力具备以下特征：

- 可替换（MyBatis / JPA / JDBC / NoSQL）
- 非所有插件必需
- 可裁剪、可组合
- 强实现属性而非抽象属性

这些特征与插件模型**天然契合**，而非 infra。

---

### 4. “无插件启动”不是必须目标

平台采用如下原则：

- **系统启动 ≠ 业务可用**
- 平台最小可运行集由“系统插件”提供
- 无任何插件的启动失败属于**设计预期**

平台通过内置系统插件（随系统发布、默认启用、不可卸载）
而不是 infra 层，来解决启动闭包问题。

---

## 决策结果（Consequences）

### 正面影响

- 架构边界显著简化
- 插件成为唯一能力来源，语义清晰
- 避免 infra 演化为“影子 core”
- 插件治理、版本管理、裁剪能力增强
- 平台范式保持一致性与长期可演进性

### 负面影响 / 代价

- 初期工程便利性略有下降
- 所有通用能力必须以插件形式交付
- 需要明确系统插件与业务插件的治理规则

---

## 取消 infra 后的目标架构

### 新模块结构

```
backend-platform/
├─ platform-core/ # 平台内核：SPI + 契约（无实现）
├─ platform-plugin/ # 插件 API + 插件运行时 + 宿主能力
├─ platform-app/ # Spring Boot 启动器 / 装配器
└─ plugins/
├─ system-plugins/ # 系统插件（官方、默认启用）
│ ├─ system-user
│ ├─ system-auth
│ ├─ system-orm-mybatis
│ └─ system-common-utils
└─ business-plugins/ # 业务 / AI / 扩展插件
```

---

## 各模块职责说明（决策后）

### platform-core

**职责：**

- 定义所有 SPI（领域 / 技术 / 平台能力）
- 定义插件契约、生命周期接口
- 定义平台级抽象模型与约束

**禁止事项：**

- ❌ 任何 SPI 实现
- ❌ 技术框架依赖（ORM / Web / DB / AI SDK）

---

### platform-plugin

**职责：**

- 插件加载机制（ClassLoader / ModuleLayer）
- 插件发现（目录 / 仓库 / 索引）
- 插件生命周期管理
- SPI 绑定与仲裁（优先级 / 条件 / 排序）
- 插件隔离、安全与沙箱
- PluginContext 与运行期上下文

**定位：**

> 插件平台运行时（Plugin Runtime / Host）

---

### platform-app

**职责：**

- Spring Boot 启动
- 平台装配与配置
- 启动插件运行时
- 暴露运维、健康检查、基础入口

**禁止事项：**

- ❌ 业务逻辑
- ❌ SPI 实现

---

### plugins（含 system-plugins）

**职责：**

- 提供所有 SPI 的具体实现
- 包括业务能力、系统能力、技术能力

**系统插件（System Plugins）约定：**

- 随平台发布
- 默认启用
- 不可卸载（或需显式配置）
- 仍遵循插件生命周期与隔离规则

---

## 结论（Summary）

> 取消 `platform-infra` 模块不是功能削减，  
> 而是平台范式成熟后的**结构性收敛**。

该决策确保：

- 插件是唯一的能力实现单元
- core 保持纯粹抽象
- 平台长期演进路径清晰且可控

这是一次**为一致性而牺牲局部便利性**的有意识决策。
