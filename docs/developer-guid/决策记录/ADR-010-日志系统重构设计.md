# ADR-010: 日志系统重构设计

---

**决策状态：已接受（已实施）**

## 背景与问题

Nexus Admin 平台已具备日志系统的基础骨架（`LogWriter` 扩展点、`LogService` 管理接口、`InMemoryLogService` 默认实现、`LogController` 管理面板 API、`LogEntry` 领域模型），形成了"写入 → 存储 → 查询"的三段式设计意图。

但当前存在以下能力缺口：

### 问题一：LogWriter 扩展点无实现，写链路未贯通

`LogWriter` 作为 ExtensionPoint 已定义 `write(LogEntry, InvocationContext)` 写入契约，但项目中没有任何实现类。`InMemoryLogService.append()` 方法虽已准备就绪，却无任何调用方——管理面板查询不到任何日志数据，LogWriter 与 LogService 之间存在断桥。

### 问题二：各组件绕过平台日志体系，直接使用 SLF4J

`AuthFilter`、`AiAutoConfig`、`DefaultUIContributionRegistry` 等组件直接使用 `org.slf4j.Logger` 输出日志，未经过 `LogWriter` 统一入口。这导致：

- 日志分散在多处，无法在管理面板统一查询
- 缺少统一的上下文注入（traceId、userId、tenantId 等）
- 无法利用 LogWriter 扩展点实现日志路由到第三方系统

### 问题三：写入与存储职责混合

`InMemoryLogService` 同时实现 `LogService`（查询管理）和提供 `append()` 方法（写入存储），职责边界模糊。若未来需要替换存储实现（如切换到 Elasticsearch），写入方和查询方将被迫耦合在同一实现中。

### 问题四：缺少框架级桥接机制

参考 AI 体系中 `ChatLanguageModel` 桥接 `AiProvider` 的做法（平台通过一个桥接 Bean 无缝适配 LangChain4j），日志系统缺少类似的 SLF4J/Logback 桥接层，导致开发者无法以零侵入方式使用平台日志能力。

---

## 决策目标

从日志体系统一性视角，重构平台的日志系统，使其：

1. **写链路贯通**：SLF4J 日志 → Logback Appender → LogWriter → LogStorage，形成完整数据流
2. **框架无缝桥接**：通过 Logback Appender 自动拦截所有 SLF4J 日志，开发者无需改变 `log.info()` 的使用习惯
3. **写入与存储解耦**：LogWriter（怎么写）、LogStorage（怎么存怎么查）、LogService（怎么管）三者职责清晰分离
4. **可扩展可替换**：LogWriter 和 LogStorage 均可通过插件扩展或替换
5. **管理面板透明**：LogController/LogService 不感知底层存储实现
6. **遵循扩展点体系**：LogWriter 作为 ExtensionPoint，支持多实现竞争与运行时替换

---

## 决策方案

### 议题一：写入与存储的接口分离

#### 当前问题

`InMemoryLogService` 同时承担「写入（`append`）」与「查询管理（`query`/`cleanup`）」两种职责，违背单一职责原则。

#### 可选方案对比

| 维度 | A. LogWriter + LogStorage 分离（推荐） | B. 保持现有混合模式 |
|------|--------------------------------------|-------------------|
| 职责单一性 | ✅ 写入/存储/管理三层各司其职 | ❌ 写入与存储耦合 |
| 可替换性 | ✅ LogWriter 和 LogStorage 可独立替换 | ❌ 替换存储必须同时触及写入逻辑 |
| 与 AI 体系一致性 | ✅ 类比 AiProvider（能力）、AiToolRegistry（注册）、AIToolProvider（桥接）的分层 | ❌ 无对应 |
| 插件扩展灵活度 | ✅ 插件可仅替换写入（如转发到 ELK），或仅替换存储（如切换到 ES） | ❌ 只能整体替换 |

#### 决策结论

**分离为三个独立接口，形成清晰的三层架构：**

```
┌─────────────────────────────────────────────────────────┐
│                    日志系统三层架构                        │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌───────────────────────────────────────────────────┐  │
│  │   LogWriter（写入扩展点，ExtensionPoint）            │  │
│  │   • 定义日志写入契约                                │  │
│  │   • write(LogEntry, InvocationContext)             │  │
│  │   • 插件可提供自定义实现（ELK/Loki/文件/Kafka 等）   │  │
│  │   • 职责：日志写到哪                                │  │
│  └───────────────────────────────────────────────────┘  │
│                         │                                │
│                         ▼                                │
│  ┌───────────────────────────────────────────────────┐  │
│  │   LogStorage（存储抽象，非 ExtensionPoint）          │  │
│  │   • 定义日志存储与查询契约                           │  │
│  │   • 默认 InMemoryLogStorage（供管理面板）           │  │
│  │   • 可替换为 ES/数据库 等实现                       │  │
│  │   • 职责：日志怎么存、怎么查                         │  │
│  └───────────────────────────────────────────────────┘  │
│                         │                                │
│                         ▼                                │
│  ┌───────────────────────────────────────────────────┐  │
│  │   LogService（管理门面，非 SPI）                     │  │
│  │   • 面向管理面板的统一查询与管理入口                  │  │
│  │   • 委托 LogStorage 完成查询/清理                   │  │
│  │   • 提供保留策略、统计等管理层能力                   │  │
│  │   • 不感知 LogWriter，不感知存储具体实现             │  │
│  └───────────────────────────────────────────────────┘  │
│                                                         │
│  ═══════════════ 桥接层 ═══════════════                  │
│  ┌───────────────────────────────────────────────────┐  │
│  │   LogbackLogWriter（Logback Appender 桥接）         │  │
│  │   • 继承 AppenderBase<ILoggingEvent>              │  │
│  │   • 自动拦截所有 SLF4J 日志                        │  │
│  │   • 转换 ILoggingEvent → LogEntry                │  │
│  │   • 委托 LogWriter.write()                        │  │
│  └───────────────────────────────────────────────────┘  │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**决策依据：**

- LogWriter（ExtensionPoint）关注"日志的外部去向"——ELK、Loki、文件、Kafka 等，属于运行时能力，可多实现竞争
- LogStorage（非 ExtensionPoint）关注"日志的内部存储与查询"——内存、ES、数据库等，是平台内建能力，单一实现即可
- LogService 是面向管理面板的统一门面，屏蔽底层存储细节
- 此分离使开发者可以独立替换写入通道（如将日志转发到 Kafka）而不影响管理面板查询，或替换存储引擎（如切换到 ES）而不影响日志写入链路

### 议题二：SLF4J 桥接方式

#### 背景

项目使用 Spring Boot，其默认日志框架为 Logback（实现了 SLF4J）。需要将 SLF4J 日志自动汇入平台日志系统。

#### 可选方案对比

| 维度 | A. Logback Appender（推荐） | B. 自定义 PlatformLogger 包装类 |
|------|---------------------------|-------------------------------|
| 零代码侵入 | ✅ 所有现有 `log.info()` 自动汇入 | ❌ 需改造所有调用点为 `PlatformLogger.info()` |
| 第三方库日志覆盖 | ✅ 自动捕获 Spring、Hibernate 等框架日志 | ❌ 第三方库无法改造 |
| 开发者学习成本 | ✅ 无额外学习成本，沿用 SLF4J | ❌ 需学习新 API |
| 与 Spring Boot 兼容 | ✅ 原生支持，自动装配 | ✅ 不依赖 Logback |
| 上下文注入 | ✅ 通过 MDC 自动注入 traceId/userId | ⚠️ 需手动传递 |
| 框架耦合 | ⚠️ 依赖 Logback API | ✅ 不依赖具体框架 |

#### 决策结论

**采用 Logback Appender 作为默认桥接实现**（`LogbackLogWriter`），实现 `ch.qos.logback.core.AppenderBase<ILoggingEvent>`。

```java
// LogbackLogWriter 同时实现 LogWriter，作为默认的日志写入实现
public class LogbackLogWriter extends AppenderBase<ILoggingEvent> implements LogWriter {

    private final LogStorage logStorage;

    @Override
    protected void append(ILoggingEvent event) {
        LogEntry entry = LogEntry.builder()
                .type(LogType.SYSTEM)
                .level(convertLevel(event.getLevel()))
                .message(event.getFormattedMessage())
                .traceId(MDC.get("traceId"))
                .userId(MDC.get("userId"))
                .tenantId(MDC.get("tenantId"))
                .channelId(MDC.get("channelId"))
                .attribute("logger", event.getLoggerName())
                .attribute("thread", event.getThreadName())
                .build();
        logStorage.store(entry);
    }

    @Override
    public void write(LogEntry entry, InvocationContext context) {
        // 直接写入结构化日志（供插件或代码显式调用）
        LogEntry enriched = enrichFromContext(entry, context);
        logStorage.store(enriched);
    }
}
```

**与 AI 体系桥接模式对比：**

| 层面 | AI 体系 | 日志体系 |
|------|--------|---------|
| 能力扩展点 | `AiProvider extends ExtensionPoint` | `LogWriter extends ExtensionPoint` |
| 框架桥接 | `ChatLanguageModel`（委托 AiProvider） | `LogbackLogWriter`（拦截 SLF4J → 委托 LogWriter） |
| 桥接方向 | 平台 → 框架（平台能力适配框架接口） | 框架 → 平台（框架日志汇入平台系统） |
| 可选装配 | `@ConditionalOnClass("langchain4j")` | Logback 随 Spring Boot 自动装配 |

**决策依据：**

- Spring Boot 默认使用 Logback，集成零配置
- 开发者完全不需要学习新 API，`log.info()` 即可自动汇入平台日志
- Spring、Hibernate、Tomcat 等框架日志自动覆盖
- MDC（Mapped Diagnostic Context）天然支持上下文注入，与 `InvocationContext` 的 traceId/userId 等字段对齐
- 若未来需要支持其他日志框架（Log4j2），可通过同一 LogWriter 扩展点新增 Appender 实现

### 议题三：LogStorage 接口职责范围

#### 可选方案对比

| 维度 | A. LogStorage 纯存储 + LogService 管理层（推荐） | B. LogStorage 同时包含查询和管理 |
|------|-----------------------------------------------|-------------------------------|
| 职责清晰度 | ✅ 存储只管存/查，LogService 管策略和统计 | ⚠️ 策略逻辑混入存储层 |
| 可替换性 | ✅ 替换存储不影响保留策略 | ❌ 每个存储实现需各自实现策略 |
| 管理面板对接 | ✅ LogController 仅依赖 LogService | ⚠️ Controller 可能需要感知存储细节 |

#### 决策结论

**LogStorage 仅负责日志条目的基本存取，保留策略与统计等管理层逻辑归属 LogService。**

**LogStorage 接口定义：**

```java
package com.nexusadmin.api.log;

import com.nexusadmin.api.domain.log.LogEntry;
import com.nexusadmin.api.domain.result.PageResult;
import java.time.Instant;

/**
 * 日志存储抽象，定义日志条目的持久化与查询契约。
 *
 * <p>与 LogWriter 职责分离：LogWriter 负责"日志写到哪"，
 * LogStorage 负责"日志怎么存、怎么查"。</p>
 */
public interface LogStorage {

    /** 存储一条日志条目 */
    void store(LogEntry entry);

    /** 按条件分页查询日志 */
    PageResult<LogEntry> query(LogType type, LogLevel level, String keyword,
                               Instant from, Instant to, int page, int size);

    /** 删除早于指定时间的日志条目，返回删除数量 */
    long removeBefore(Instant timestamp);

    /** 获取当前日志条目总数 */
    long count();
}
```

**LogService 保留现有接口不变，内部委托 LogStorage：**

```java
public class DefaultLogService implements LogService {

    private final LogStorage logStorage;
    private volatile LogRetentionConfig retentionConfig;  // 保留策略

    @Override
    public PageResult<LogEntry> query(...) {
        return logStorage.query(type, level, keyword, from, to, page, size);
    }

    @Override
    public long cleanupExpired() {
        Instant cutoff = computeCutoff(retentionConfig);
        return logStorage.removeBefore(cutoff);
    }
}
```

**决策依据：**

- LogStorage 保持最小化接口，降低替换成本
- 保留策略、清理调度等管理层逻辑统一在 LogService 中，不随存储实现变化
- LogController 仅依赖 LogService，对底层存储完全透明
- 符合「LogController-LogService 不关心日志系统的具体实现和存储方式」的要求

### 议题四：LogService 接口调整

#### 决策结论

**LogService 接口保持不变**，现有 `query`、`getRetentionConfig`、`updateRetentionConfig`、`cleanupExpired` 方法签名均不动。`DefaultLogService` 内部将 `InMemoryLogService` 的职责拆分为：

- 委托 `LogStorage` 完成 `query` / `removeBefore`
- 自身管理 `LogRetentionConfig` 和清理策略

**LogRetentionConfig 增强**：支持按 LogType 差异化保留期限（当前接口已定义 `auditRetention`、`errorRetention` 字段，但 `InMemoryLogService.cleanupExpired()` 未使用）。

### 议题五：LogWriter 默认实现与存储的装配关系

#### 设计方案

`LogbackLogWriter` 作为 `LogWriter` 的默认实现，同时承担两个角色：
- **Logback Appender**：拦截 SLF4J 日志事件
- **LogWriter 实现**：接收显式的结构化日志写入

两者均委托 `LogStorage` 完成最终存储。

**装配关系：**

```
LogAutoConfig
│
├── LogStorage (default: InMemoryLogStorage)
│     @ConditionalOnMissingBean(LogStorage.class)
│
├── LogWriter (default: LogbackLogWriter)
│     @ConditionalOnMissingBean(LogWriter.class)
│     注入 LogStorage，自动附加到 Root Logger
│
├── LogService (default: DefaultLogService)
│     @ConditionalOnMissingBean(LogService.class)
│     注入 LogStorage，封装查询与保留策略管理
│
└── LogRetentionScheduler（可选）
      @ConditionalOnProperty("panel.log.auto-cleanup")
      定时触发 LogService.cleanupExpired()
```

**数据流路径：**

```
路径一（隐式，默认路径）：
  SLF4J log.info() → LogbackLogWriter(Appender) → LogStorage.store()

路径二（显式，结构化日志）：
  插件代码 → LogWriter.write(LogEntry, context) → LogbackLogWriter → LogStorage.store()

路径三（查询管理）：
  LogController → LogService.query() → LogStorage.query()
```

### 议题七：AbstractPlugin 生命周期日志

#### 决策结论

在 `AbstractPlugin` 的四个 `final` 回调方法（`onInitialize`、`onStart`、`onStop`、`onUnload`）中注入 SLF4J 日志输出：

| 回调方法 | 日志级别 | 日志内容 |
|---------|---------|---------|
| `onInitialize` | DEBUG | 插件 [pluginId] 正在初始化 / 初始化完成 |
| `onStart` | INFO | 插件 [pluginId] 正在启动 / 启动完成 |
| `onStop` | INFO | 插件 [pluginId] 正在停止 / 停止完成 |
| `onUnload` | DEBUG | 插件 [pluginId] 正在卸载 / 卸载完成 |

日志定义在 `final` 的 `onXxx` 方法中（不可被子类覆盖），确保所有插件自动获得统一的声明周期日志。这些日志通过 SLF4J 输出后，自动被 `LogbackLogWriter` 拦截汇入平台日志体系。

此设计**不影响** core 模块的零框架依赖约束——core 模块仅依赖 SLF4J API（`org.slf4j`），SLF4J 本身是一个纯接口层，不引入具体日志框架实现。

### 议题八：LogType 可扩展化与日志分类体系重设计

#### 背景

当前 `LogType` 为 `enum` 类型，定义 SYSTEM、AUDIT、AI、TECH 四种值。该设计存在两个结构性问题：

1. **不可扩展**：enum 值在编译时固定，插件无法注册自定义日志类型。这与平台「一切能力都是扩展点」的架构原则相悖。
2. **分类混乱**：AI（子系统维度）、TECH（技术维度）、AUDIT（安全维度）、SYSTEM（运行维度）混杂了不同维度的分类标准。后续若加入 LOGIN、API 等枚举值，类型数量会持续膨胀，且分类边界模糊。

#### 方案：参照 EventScope 模式，LogType 由 enum 重构为 final class

平台中 [EventScope](file:///c:/Users/starl/Desktop/1_Project/20260124_插件化业务拓展平台/backend/nexus-admin-core/src/main/java/com/nexusadmin/core/event/EventScope.java) 采用了 **final class + 静态工厂方法 + custom() 逃逸** 的扩展友好模式，已被事件系统和配置中心验证有效。LogType 应遵循相同模式：

```java
public final class LogType {
    private final String category;  // 主分类（system / audit）
    private final String name;      // 子类型名称

    private LogType(String category, String name) {
        this.category = Objects.requireNonNull(category);
        this.name = Objects.requireNonNull(name);
    }

    // ═══ 内置标准常量 ═══
    public static final LogType SYSTEM = new LogType("system", "general");
    public static final LogType AUDIT = new LogType("audit", "general");

    // ═══ 内置常用子类型工厂方法 ═══
    public static LogType systemPluginLifecycle() { return new LogType("system", "plugin-lifecycle"); }
    public static LogType systemApiRequest()     { return new LogType("system", "api-request"); }
    public static LogType systemConfigChange()   { return new LogType("system", "config-change"); }
    public static LogType auditLogin()           { return new LogType("audit", "login"); }
    public static LogType auditPermission()      { return new LogType("audit", "permission"); }
    public static LogType auditOperation()       { return new LogType("audit", "operation"); }

    // ═══ 插件扩展入口 ═══
    public static LogType of(String category, String name) {
        return new LogType(category, name);
    }

    // getters, equals, hashCode, toString, JSON 序列化...
}
```

**与 EventScope 模式对标：**

| 概念 | EventScope | LogType（新） |
|------|-----------|--------------|
| 不可变性 | `final class`，构造即 snapshot | 同 |
| 分类轴 | `category`（global/platform/plugin/tenant） | `category`（system/audit） |
| 标识轴 | `identifier`（插件ID/租户ID） | `name`（login/permission 等） |
| 扩展入口 | `EventScope.custom(category, identifier)` | `LogType.of(category, name)` |
| 内置常量 | `EventScope.global()`, `EventScope.platform()` | `LogType.SYSTEM`, `LogType.AUDIT` |
| equals/hashCode | 基于 `category` + `identifier` | 基于 `category` + `name` |
| toString() | `category:identifier` | `category/name` |

#### 分类体系：二维精简模型

仅保留两个主分类（category），涵盖平台全部日志场景：

| category | 含义 | 适用场景 | 典型 typeName |
|----------|------|---------|--------------|
| `system` | 平台运行日志 | 插件生命周期、配置变更、API 请求、AI 调用、定时任务、错误堆栈、所有 SLF4J 默认路径的日志 | `general`、`plugin-lifecycle`、`api-request`、`config-change` |
| `audit` | 安全审计日志 | 登录/登出、权限检查、敏感数据访问、用户操作留痕（不可否认性要求） | `general`、`login`、`permission`、`operation` |

**设计原则：**

- **category 极简（只有 2 个）**：避免类型膨胀。system 收纳所有运行期日志（原 SYSTEM + AI + TECH + API），audit 收纳所有安全审计日志（原 AUDIT + LOGIN）。
- **name 自由扩展**：插件通过 `LogType.of("system", "custom-event")` 或 `LogType.of("audit", "data-export")` 创建子类型，无需修改核心代码。
- **JSON 序列化统一**：`@JsonValue` → `"category/name"`，`@JsonCreator` 反向解析。现有 LogEntry 的 `type` 字段仅是类型从 enum 变为 class，record 结构不变。

#### 与传统方案的对比

| 维度 | 旧方案（enum 枚举堆砌） | 新方案（class 二维模型） |
|------|----------------------|----------------------|
| 类型数量 | 随子系统线性增长（SYSTEM、AUDIT、AI、TECH、LOGIN、API...）→ 无限膨胀 | 恒定为 2 个 category，name 维度自由扩展 |
| 插件扩展 | ❌ enum 无法扩展，需修改核心代码 | ✅ `LogType.of("system", "xxx")` 零成本扩展 |
| 分类一致性 | ❌ 混用子系统维度（AI）、技术维度（TECH）、安全维度（AUDIT） | ✅ 统一按「运行/审计」维度划分 |
| 管理面板筛选 | ✅ `?type=SYSTEM` | ✅ `?category=system`（粗筛选）、`?category=audit&typeName=login`（精确筛选） |
| JSON 序列化 | 默认 `"SYSTEM"` | `"system/general"`，向后兼容可通过 Converter 适配 |

#### 对 LogStorage / LogService 查询接口的影响

查询接口由传递 `LogType type` 改为传递 `String category` + `String typeName`：

```java
// LogStorage（新签名）
PageResult<LogEntry> query(String category, String typeName, LogLevel level,
                            String keyword, Instant from, Instant to, int page, int size);

// LogService（新签名）
PageResult<LogEntry> query(String category, String typeName, LogLevel level,
                            String keyword, Instant from, Instant to, int page, int size);
```

**理由**：
- `category` 和 `typeName` 均为 String，不绑定任何编译期常量，插件自定义类型可直接作为字符串传入
- `category` 为 null 时匹配所有分类，`typeName` 为 null 时匹配该分类下所有子类型
- 管理面板 API：`GET /admin/v1/logs?category=audit&typeName=login&level=WARN`

#### 插件扩展场景示例

**场景 1：业务插件创建自定义日志类型**

```java
// 在插件代码中
LogType ORDER_CREATED = LogType.of("system", "order-created");
LogEntry entry = LogEntry.builder()
        .type(ORDER_CREATED)
        .level(LogLevel.INFO)
        .message("订单创建成功: " + orderId)
        .build();
logWriter.write(entry, context);
```

**场景 2：审计插件注册审计事件类型**

```java
LogType DATA_EXPORT = LogType.of("audit", "data-export");
// 管理面板通过 ?category=audit&typeName=data-export 检索
```

**场景 3：管理面板按分类/类型组合筛选**

| URL | 含义 |
|-----|------|
| `GET /admin/v1/logs?category=system` | 全部系统运行日志 |
| `GET /admin/v1/logs?category=audit` | 全部安全审计日志 |
| `GET /admin/v1/logs?category=audit&typeName=login` | 仅登录相关审计日志 |
| `GET /admin/v1/logs?category=system&typeName=plugin-lifecycle` | 插件生命周期日志 |

#### 决策结论

**采用 LogType class（参照 EventScope）+ 二维分类（category + name）+ 查询接口 String 化**。

- LogType 由 enum 重构为 `public final class`，category 极简为 `system` / `audit` 两个值
- name 自由扩展，插件通过 `LogType.of(category, name)` 创建自定义类型
- LogStorage / LogService 查询接口改为 `String category, String typeName` 参数，天然支持任意自定义类型过滤
- 无需额外扩展点或注册表——LogType 本身即扩展友好的值对象，与 EventScope 设计一致

## 影响范围评估

| 模块 | 影响说明 | 风险等级 |
|------|---------|---------|
| nexus-admin-core | 仅 `AbstractPlugin.java` 新增 SLF4J Logger + 生命周期日志输出（~16 行代码）。SLF4J API 为纯接口层，不破坏 core 模块零框架依赖原则 | 低 |
| nexus-admin-api | 新增 5 个文件（LogStorage、LogbackLogWriter、InMemoryLogStorage、DefaultLogService、LogAutoConfig）+ 4 个 LogFactory 文件、删除 1 个文件（InMemoryLogService）、修改 3 个文件（LogType.java 重构为 class、ServicesAutoConfig、LogService 接口） | 中（LogType 重构涉及类型变更） |
| nexus-admin-app | 无强制修改（LogAutoConfig 自动装配） | 无 |
| plugins | 现有插件无影响。插件可选实现 `LogWriter` 提供自定义日志输出，或通过 `LogType.of()` 创建自定义日志类型 | 无 |

**修改的现有接口：**
- `LogType.java`：由 `enum` 重构为 `public final class`（遵循 EventScope 模式），原枚举值 SYSTEM/AUDIT 改为同名静态常量
- `LogService.java`：`query` 方法签名由 `(LogType type, ...)` 改为 `(String category, String typeName, ...)`
- `LogStorage.java`：`query` 方法签名同上变更

**不修改的现有接口：** `LogWriter`、`LogEntry`、`LogLevel`、`LogController` 均无修改。

**删除的文件：** `InMemoryLogService.java`，其职责拆分到 `InMemoryLogStorage`（存储）+ `DefaultLogService`（管理）。

## 总结

### 核心决策一览

| 决策项 | 结论 | 关键依据 |
|-------|------|---------|
| 写入与存储分离 | LogWriter（ExtensionPoint）+ LogStorage（存储 SPI）+ LogService（管理门面）三层独立 | 职责单一，与 AI 体系分层对齐 |
| SLF4J 桥接 | Logback Appender（`LogbackLogWriter`）自动拦截，同时实现 LogWriter | 零代码侵入，Spring Boot 默认兼容 |
| LogStorage 职责 | 纯存取接口（store/query/removeBefore/count），策略归 LogService | 最小化接口，降低替换成本 |
| LogType 可扩展化 | enum → `final class`（参照 EventScope），category 极简（system/audit 二维），name 自由扩展 | 插件可通过 `LogType.of()` 创建自定义类型，无需修改核心代码 |
| LogService 查询接口 | `query(LogType type, ...)` → `query(String category, String typeName, ...)` | String 参数天然支持任意自定义类型筛选 |
| 默认 LogWriter | `LogbackLogWriter` 同时作为 Appender 和 LogWriter 实现 | 双重角色，两条路径汇入同一存储 |
| 模块归属 | 全部置于 `nexus-admin-api` | 与 AI 体系同层，引入即用 |
| AbstractPlugin 日志 | `final` 回调方法内注入 DEBUG/INFO 级别日志 | 不可覆盖，统一标准化 |

### 设计原则贯彻

| 原则 | 体现 |
|------|------|
| **框架无缝桥接** | Logback Appender 自动拦截 SLF4J，开发者 `log.info()` 即用，与 AI 体系 `ChatLanguageModel` 桥接模式一致 |
| **写入与存储解耦** | LogWriter（怎么写）、LogStorage（怎么存查）、LogService（怎么管）三层独立，可各自替换 |
| **自定义类型可扩展** | LogType 由 enum 重构为 class（EventScope 模式），`LogType.of()` 开放扩展；查询接口使用 String 参数，任意自定义类型可被检索 |
| **管理面板透明** | LogController → LogService → LogStorage，不感知 LogWriter 和具体存储实现 |
| **扩展点体系一致** | LogWriter 作为 ExtensionPoint 支持多实现竞争与运行时替换，与 AiProvider 模式一致 |
| **零技术债** | 删除混合职责的 InMemoryLogService，职责拆分清晰；消除 enum 不可扩展的架构瓶颈 |
| **不破坏 core 零框架依赖** | SLF4J API 是纯接口层（`org.slf4j` 仅 3 个类），不引入 Logback 等具体实现依赖 |

### 长期演进方向

1. **异步日志写入**：`LogbackLogWriter` 可扩展为异步 Appender（队列 + 批量写入），降低日志对主业务的性能影响
2. **多种存储后端**：`LogStorage` 可扩展为 `ElasticsearchLogStorage`、`DatabaseLogStorage`、`FileLogStorage` 等
3. **日志级别动态调整**：通过 `LogService` 暴露日志级别调整 API，对接管理面板
4. **日志聚合网关**：多 `LogWriter` 实现可同时生效（如同时写入内存 + 转发 Kafka），由 `CompositeLogWriter` 组合
5. **独立模块提取**：若未来日志体量显著增长，可将 `log/` 包独立为 `nexus-admin-log` 模块
