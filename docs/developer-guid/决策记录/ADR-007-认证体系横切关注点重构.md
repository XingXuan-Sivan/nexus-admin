# ADR-007: 认证体系横切关注点重构

---

## 背景与问题

### 1. 已有决策回顾

ADR-005 议题四确立了认证 Token 管理与权限可拓展模型的核心决策：

- Token 端点契约：`/admin/v1/auth/login`、`/admin/v1/auth/logout`、`/admin/v1/auth/refresh`
- `PermissionResolver` 拓展点 + `@RequirePermission` 注解实现权限声明式校验
- `AuthProvider` 拓展点 + `CompositeAuthProvider` 责任链实现认证可替换
- `AuthChallengeHandler` 拓展点实现认证失败响应的策略可替换

ADR-005 代码实现审阅中已确认，实际代码在架构上优于设计——认证（`AuthFilter`）与授权（`PermissionInterceptor`）分离，职责更清晰。

### 2. 当前代码存在的问题

经过对认证体系相关代码的全面审查，发现以下四类问题：

**问题一：横切关注点感知具体版本号，违反开闭原则**

`AuthFilter` 拦截路径和 `PermissionInterceptor` 注册路径均硬编码了 `/admin/v1`：

```java
// AuthFilter.java — 只匹配版本化路径
private static final String ADMIN_PATH_PREFIX = "/admin/v1";

// AuthAutoConfig.java — 过滤器 URL 模式绑定版本
registration.addUrlPatterns("/admin/v1/*");

// WebMvcAutoConfig.java — 拦截器路径模式绑定版本
registry.addInterceptor(permissionInterceptor)
        .addPathPatterns("/admin/v1/**");
```

认证、授权、日志、限流等横切关注点应对所有版本通用。拦截器感知具体版本导致每次 API 版本升级都需要修改鉴权配置，违背了"对扩展开放，对修改关闭"原则。

**问题二：通用路径与配置项分散硬编码**

公开端点白名单以 if-else 硬编码在 `AuthFilter.isPublicEndpoint()` 中：

```java
if ("POST".equalsIgnoreCase(method) && LOGIN_PATH.equals(path)) { return true; }
if (path.startsWith("/v3/api-docs/")) { return true; }
if ("/doc.html".equals(path)) { return true; }
if (path.startsWith("/webjars/")) { return true; }
```

同类路径常量在多处重复定义（如 `LOGIN_PATH` 在 `AuthFilter` 和 `BootstrapAuthChallengeHandler` 中各自声明），缺乏统一管理。

**问题三：Token/Session 工具逻辑重复**

以下通用逻辑在多个类中各自实现：

| 方法 | 重复位置 |
|------|---------|
| `extractBearerToken()` | `AuthFilter` (L226)、`AuthController` (L135) |
| `parseBasicAuth()` | `AuthFilter` (L283) — 未提取为可复用工具 |
| `getSessionUser()` | `AuthFilter` (L309)、`PermissionInterceptor` (L116) |
| `SESSION_ATTR_USER` | `AuthFilter` (L60)、`PermissionInterceptor` (L35) |

**问题四：默认登录页及其关联组件冗余**

`BootstrapAuthChallengeHandler` 与 `bootstrap-login.html` 提供了一套基于 Session/RGB 模式的 HTML 表单登录机制。在 ADR-005 已将登录标准化为 JSON API 端点后，这套 HTML 登录机制已成为冗余，且与统一的 API 风格不一致。

### 3. 根本原因

| 问题 | 根因 |
|------|------|
| 版本号硬编码 | 横切关注点组件直接使用了 Controller 层的版本化路径，未区分"路由版本"与"拦截基路径"两个概念 |
| 路径硬编码 | 缺乏统一的配置属性类管理可配置路径，缺乏常量类收敛不可变协议常量 |
| 工具逻辑重复 | Token/Session 操作被视为"业务逻辑"散落在各组件中，未识别其为通用横切工具 |
| 登录页冗余 | ADR-005 决策后未同步清理旧实现，BootstrapAuthChallengeHandler 与新的 API 登录流不一致 |

---

## 决策方案

采用**基路径拦截 + 配置属性化 + 工具类收敛 + 冗余删除**四项措施：

1. **基路径拦截**：`AuthFilter` 和 `PermissionInterceptor` 只匹配 `/admin/**`，不感知版本号
2. **配置属性化**：可配置的路径收敛至 `PanelWebProperties`（`@ConfigurationProperties(prefix = "panel.web")`），支持 yml 自定义
3. **工具类收敛**：HTTP 认证通用逻辑封装至 `HttpAuthUtils`，消除跨类重复
4. **冗余删除**：移除 `BootstrapAuthChallengeHandler` 和 `bootstrap-login.html`，统一使用 `DefaultAuthChallengeHandler`（401 JSON 响应）

### 新增组件设计

#### PanelWebProperties（配置属性类）

```java
// 路径: api/config/properties/PanelWebProperties.java
@ConfigurationProperties(prefix = "panel.web")
public class PanelWebProperties {

    /** 管理面板 API 基础路径，默认 "/admin" */
    private String basePath = "/admin";

    /** 公开端点路径列表，支持 Ant 风格模式 */
    private List<String> publicEndpoints = List.of(
            "/admin/auth/login",
            "/doc.html",
            "/webjars/**",
            "/v3/api-docs/**"
    );

    // getters/setters ...
}
```

**设计要点**：

- `basePath` 不含版本号，过滤器/拦截器仅感知到 `/admin` 层级
- `publicEndpoints` 使用 Ant 风格（如 `/webjars/**`），通过 `AntPathMatcher` 统一匹配
- yml 配置前缀 `panel.web`，与应用名解耦

**yml 配置对应**：

```yaml
panel:
  web:
    base-path: /admin
    public-endpoints:
      - /admin/auth/login
      - /doc.html
      - /webjars/**
      - /v3/api-docs/**
```

#### HttpAuthUtils（HTTP 认证工具类）

```java
// 路径: api/util/HttpAuthUtils.java
public final class HttpAuthUtils {

    private HttpAuthUtils() {}

    private static final String AUTH_HEADER = "Authorization";
    private static final String BEARER_PREFIX = "Bearer ";
    private static final String BASIC_PREFIX = "Basic ";
    private static final String SESSION_ATTR_USER = "authenticatedUser";

    /** 从请求中提取 Bearer Token */
    public static String extractBearerToken(HttpServletRequest request) { ... }

    /** 解析 Basic 认证头，返回 [username, password] */
    public static String[] parseBasicAuth(String authHeader) { ... }

    /** 从 Session 获取已认证用户标识 */
    public static String getSessionUser(HttpServletRequest request) { ... }

    /** 将用户标识存入 Session */
    public static void setSessionUser(HttpServletRequest request, String userId) { ... }
}
```

**设计要点**：

- 纯静态工具类，禁止实例化
- 协议级常量（`"Bearer "`、`"Authorization"`、`"authenticatedUser"`）私有化，不对外暴露
- 无 Spring 依赖，可独立单测

### 现有组件变更

#### AuthFilter 重构要点


| 变化项 | 旧 | 新 |
|--------|-----|-----|
| 拦截基路径 | `"/admin/v1"` 常量 | 注入 `PanelWebProperties.basePath` |
| 公开端点判断 | 4 个 if-else 分支硬编码 | 遍历 `publicEndpoints`，`AntPathMatcher` 匹配 |
| 表单登录处理 | `extractFormCredentials()` + `getRedirectUrl()` | 整体删除（表单登录不再支持） |
| Bearer Token 提取 | 本地 `extractBearerToken()` 方法 | 调用 `HttpAuthUtils.extractBearerToken()` |
| Basic Auth 解析 | 本地 `parseBasicAuth()` 方法 | 调用 `HttpAuthUtils.parseBasicAuth()` |
| Session 读写 | 本地 `getSessionUser()`/`setSessionUser()` | 调用 `HttpAuthUtils` 对应方法 |
| `Credentials` 记录 | 含 `isFormPost` 字段 | 简化为不可变参数传递，或直接用 `AuthRequest` |
| 依赖数量 | 2 个（`CompositeAuthProvider` + `ExtensionConsumer`） | 3 个（新增 `PanelWebProperties`） |

简化后的 `doFilter` 流程：

```
请求进入
  → 非 /admin/** → 放行
  → 公开端点（AntPathMatcher 匹配）→ 放行
  → Session 已认证 → 放行
  → Bearer Token 有效 → 存 Session → 放行
  → Basic Auth 有效 → 存 Session → 放行
  → 无凭证或失败 → challengeHandler.handleChallenge() → 401 JSON
```

#### AuthAutoConfig 变更

- **删除** `bootstrapAuthChallengeHandler()` Bean 方法
- **删除** `BootstrapAuthChallengeHandler` 的注册到扩展注册中心
- `adminAuthFilter()` URL 模式：`"/admin/v1/*"` → `"/admin/*"`
- `DefaultAuthChallengeHandler` 提升为唯一兜底（优先级最低，已满足）

#### WebMvcAutoConfig 变更

- `addPathPatterns("/admin/v1/**")` → 使用 `PanelWebProperties.basePath + "/**"`

#### AuthController 变更

- `extractBearerToken()` 本地方法 → 调用 `HttpAuthUtils.extractBearerToken()`

#### PermissionInterceptor 变更

- `getAuthenticatedUser()` → 调用 `HttpAuthUtils.getSessionUser()`
- `SESSION_ATTR_USER` 常量 → 使用 `HttpAuthUtils`（私有常量，不直接引用）

### 删除的组件


| 文件 | 删除原因 |
|------|---------|
| `BootstrapAuthChallengeHandler.java` | HTML 登录页机制已由 ADR-005 的 JSON API 登录替代 |
| `bootstrap-login.html` | 登录页面模板，随 BootstrapAuthChallengeHandler 一起移除 |

移除后，认证失败统一返回 401 + `application/problem+json`（由 `DefaultAuthChallengeHandler` 处理），与其他自定义认证实现无异。

## 备选方案对比


| 维度 | A. 基路径 + 配置属性 + 工具类 ⭐ 推荐 | B. 保持版本感知 + 仅提取常量 | C. 保持现状 |
|------|--------------------------------------|---------------------------|-----------|
| 开闭原则 | ✅ 新增版本无需改配置 | ❌ 每次版本升级改配置 | ❌ 每次版本升级改代码 |
| 路径管理 | ✅ yml 统一配置 | ⚠️ 常量类集中但不可动态覆盖 | ❌ 各文件独立硬编码 |
| 工具复用 | ✅ 单一工具类，零重复 | ❌ 仍有多处重复 | ❌ 多处重复 |
| 冗余清理 | ✅ 删除不合时宜的 HTML 登录 | ⚠️ 保留死代码 | ❌ 保留死代码 |
| 改动规模 | 中（新增2 + 修改5 + 删除2） | 小（修改4） | 无 |
| 可演进性 | ✅ 路径可配置、工具可扩展 | ⚠️ 仅解决重复问题 | ❌ |

**选择 A 的理由总结**：

1. **开闭原则**——过滤器/拦截器只匹配 `/admin/**`，版本号是 Controller 层的路由细节，不应泄漏到横切关注点
2. **单一配置源**——所有可配置路径集中在 `PanelWebProperties`，支持 yml 覆盖，无需改代码
3. **消除重复**——Token/Session 操作统一收敛到 `HttpAuthUtils`，3 个类中的重复代码归零
4. **架构一致**——与已有 `PluginProperties`（`@ConfigurationProperties(prefix = "plugin")`）模式一致
5. **不留死代码**——`BootstrapAuthChallengeHandler` 在 ADR-005 标准化 API 登录后已不合时宜，彻底移除

### 阶段 7：补充修复（Token 验证与认证挑战响应头一致性）

重构完成后在 Knife4j 测试中发现两项校验一致性缺陷，需补充修复：

**缺陷一：BootstrapAuthProvider 不支持 Bearer Token 验证**

`AuthProvider` 接口中 `login()` 默认实现生成 `"token-{userId}"` 格式的 Token，但 `validateToken()` 默认实现永返 FAILED（`"Token 验证不受支持"`）。`BootstrapAuthProvider` 仅覆写了 `authenticate()`（用户名密码校验），未覆写 `validateToken()`，导致登录成功后获得的 Token 无法通过后续请求的 Bearer Token 验证，Knife4j 中填入 Token 后依然认证失败。

**修复**：`BootstrapAuthProvider` 覆写 `validateToken()`，解析 `"token-"` 前缀格式的 Token，提取 userId 后与配置中心的用户名比对。

**缺陷二：DefaultAuthChallengeHandler 的 WWW-Authenticate: Basic 头触发浏览器弹窗**

`DefaultAuthChallengeHandler` 在 401 响应中设置了 `WWW-Authenticate: Basic realm="Admin Panel"` 响应头。该头告诉浏览器"此资源需要 Basic 认证"，浏览器收到 401 + 此头后会自动弹出原生 HTTP Basic 认证对话框（用户名/密码表单），与 API 风格的 Bearer Token 认证机制不一致。

**修复**：移除 `WWW-Authenticate` 响应头设置，认证失败仅返回 401 状态码 + JSON 错误体，由 API 客户端自行处理。

| 步骤 | 操作 | 文件 |
|------|------|------|
| 7.1 | `BootstrapAuthProvider` 覆写 `validateToken()`：验证 `login()` 生成的 `"token-{userId}"` 格式 Token | `api/auth/BootstrapAuthProvider.java` |
| 7.2 | `DefaultAuthChallengeHandler` 移除 `WWW-Authenticate: Basic` 响应头 | `api/auth/DefaultAuthChallengeHandler.java` |

修复后 Knife4j 的 BearerAuth 认证流程完整可用：登录获取 Token → 填入 Authorize → 后续请求自动携带 Bearer Token → `BootstrapAuthProvider.validateToken()` 验证通过 → 不再触发浏览器原生认证弹窗。

## 风险与缓解


| 风险 | 影响 | 可能性 | 缓解措施 |
|------|------|--------|---------|
| 删除 BootstrapAuthChallengeHandler 导致引导认证无法使用 | 无其他认证插件时系统不可登录 | 低 | `BootstrapAuthProvider` 仍然有效，`AuthController.login()` 通过 JSON API 完成认证，与 HTML 登录页无关；`DefaultAuthChallengeHandler` 作为兜底返回 401 |
| 路径 `/admin/**` 匹配范围过大 | 误拦截非管理 API | 低 | 公开端点列表包含 `/v3/api-docs/**`、`/doc.html`、`/webjars/**`，按需扩展 |

## 总结

**核心决策**：

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   PanelWebProperties → api 模块                              │
│   └─ panel.web.basePath + panel.web.publicEndpoints          │
│      yml 可配置，AntPathMatcher 匹配                          │
│                                                             │
│   HttpAuthUtils → api 模块                                   │
│   └─ extractBearerToken / parseBasicAuth / getSessionUser    │
│      纯静态工具类，消除跨类重复                               │
│                                                             │
│   AuthFilter → 只拦截 /admin/**（基路径，不感知版本）          │
│   PermissionInterceptor → 只拦截 /admin/**                   │
│                                                             │
│   BootstrapAuthProvider → 覆写 validateToken()               │
│   └─ 验证 login() 生成的 "token-{userId}" 格式 Token        │
│      Knife4j BearerAuth 认证流程完整可用                      │
│                                                             │
│   删除：BootstrapAuthChallengeHandler + bootstrap-login.html │
│   兜底：DefaultAuthChallengeHandler（401 JSON，无 WWW-Authenticate）│
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**关键收益**：

1. 拦截器/过滤器匹配基路径，新增 API 版本无需修改横切关注点配置
2. 所有可配置路径收敛至 `PanelWebProperties`，支持 yml 动态覆盖
3. Token/Session 操作统一收敛至 `HttpAuthUtils`，零重复代码
4. 移除过时的 HTML 登录机制，认证失败统一为 API 风格 401 JSON 响应
5. `BootstrapAuthProvider` 支持 Bearer Token 验证，Knife4j BearerAuth 完整可用
6. `DefaultAuthChallengeHandler` 移除 `WWW-Authenticate: Basic` 头，不再触发浏览器原生认证弹窗
7. 与项目已有 `PluginProperties` 模式一致，开发者认知成本低
