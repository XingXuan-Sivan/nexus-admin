# ADR-008: 平台接口与拓展点体系全局重构

---

## 背景与问题

Nexus Admin 项目处于早期开发阶段，已建立 Core 微内核（插件生命周期、扩展注册中心、事件总线、配置中心四大子系统）和 API 业务基础层（22 个扩展点、9 个 Controller、6 个 Service、25 个领域对象）。但随着管理面板需求的逐步明确，现有接口体系暴露出以下系统性问题：

### 问题一：Service 接口与 ExtensionPoint 职责边界模糊

当前存在两种能力暴露方式但缺乏明确的选用规则：

- **Service 类**（如 `UserService`、`RoleService`、`PermissionService`）是骨架占位，所有方法抛出 `ExtensionNotImplementedException`
- **ExtensionPoint 接口**（如 `AuthProvider`、`PermissionResolver`、`StorageProvider`）由插件实现，通过 `ExtensionRegistry` 注册

问题在于：哪些能力应作为 Service（单一实现、管理面板 CRUD），哪些应作为 ExtensionPoint（多实现竞争、运行时能力替换），从未明确定义。导致：
- `UserService` / `RoleService` / `PermissionService` 三者各自独立但语义上不可分割，替换时需同时替换三个 Service
- `LogQueryProvider` 作为 ExtensionPoint，但它本质是管理面板的查询接口，而非多实现竞争场景
- `LogRetentionPolicy` 作为独立 ExtensionPoint，但其实只是 LogQueryProvider 的一个配置维度

### 问题二：管理面板功能存在大量能力缺口

从管理面板视角审视，以下能力具备领域对象但缺少相应的 Service 接口/Controller/默认实现：

| 领域 | 领域对象 | Controller | Service | 默认实现 |
|------|---------|-----------|---------|---------|
| 用户管理 | `User` | `UserController` | `UserService`（骨架） | ❌ 无 |
| 角色管理 | `Role` | `RoleController` | `RoleService`（骨架） | ❌ 无 |
| 权限浏览 | `Permission` | `PermissionController` | `PermissionService`（骨架） | ❌ 无 |
| 字典管理 | `Dictionary`、`DictionaryItem` | ❌ 无 | ❌ 无 | ❌ 无 |
| 部门管理 | `Department` | ❌ 无 | ❌ 无 | ❌ 无 |
| 岗位管理 | `Position` | ❌ 无 | ❌ 无 | ❌ 无 |
| 日志查看 | `LogEntry` | ❌ 无 | ❌ 无 | ❌ 无 |
| 存储浏览 | — | ❌ 无 | ❌ 无 | ❌ 无 |
| 缓存检查 | — | ❌ 无 | ❌ 无 | ❌ 无 |
| 健康检查 | — | ❌ 无 | ❌ 无 | ❌ 无 |
| 事件监控 | — | ❌ 无 | ❌ 无 | ❌ 无 |

### 问题三：部分 ExtensionPoint 粒度过细或语义重叠

- **AI 领域**：`ChatProvider`、`RagProvider`、`AgentPolicy`、`ToolExecutor` 四个独立接口粒度过细、关注了过多具体技术实现（如 RAG），缺乏对AI能力的分层抽象。此外，AI 能力不应仅是"调用外部 AI"，平台自身也应能作为 AI 工具被外部调用（如 MCP 客户端模式），同时应支持 Skills、知识库等可拓展能力
- **日志领域**：`LogWriter`（写入）、`LogQueryProvider`（查询）、`LogRetentionPolicy`（保留策略）三个接口，其中 `LogQueryProvider` 和 `LogRetentionPolicy` 更适合作为管理面板 Service 而非 ExtensionPoint
- **路由领域**：`RoutingPolicy` 与 Spring MVC 的路由机制功能重叠，实际使用场景不明确

### 问题四：Core Facade 为具体类，不可替换

Core 模块的四个 Facade（`PluginFacade`、`ExtensionFacade`、`ConfigFacade`、`EventBusFacade`）均为具体类（concrete class），虽然架构文档声明"门面隔离 PluginManager 与底层组件"，但具体类形态使得框架适配（如 Spring Bean 替换）只能通过包装而非接口替换实现。

### 问题五：关联拓展点未形成统一替换单元

`AuthProvider`（认证）、`PermissionResolver`（权限）、用户-角色-权限 CRUD 三者在运行时紧密关联：认证通过后需要查询用户信息、权限校验需要查询角色-权限关联。但当前三者分别独立，替换认证插件后，管理面板的用户列表仍然调用骨架 `UserService`（抛出 501），导致认证通过但无法查看用户列表。

---

## 决策目标

从架构整体视角，成体系地设计平台全部 Service 接口与 ExtensionPoint 的：

1. **分层分类**：明确 Service 接口（管理面板 CRUD，单一实现）与 ExtensionPoint（运行时能力，多实现竞争）的边界规则
2. **缺口补齐**：为所有管理面板功能点提供对应的 Service 接口和默认实现
3. **粒度归并**：合并过细的 ExtensionPoint，删除语义重叠的接口
4. **关联内聚**：将语义上不可分割的接口聚合为统一替换单元
5. **Facade 接口化**：Core Facade 由具体类转为接口（接口定义保留在 core 模块，确保 core 作为独立 Maven 依赖时完整可用）

---

## 决策方案

### 一、接口分类体系：Service 与 ExtensionPoint 的明确边界

建立两层接口体系，按"替换粒度"和"使用场景"区分：

```
┌─────────────────────────────────────────────────────────────┐
│                    API 模块接口体系                          │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  Service 接口（管理面板 CRUD）                        │   │
│  │  • 单一实现，通过 @ConditionalOnMissingBean 替换     │   │
│  │  • 有默认内存实现，开箱即用                           │   │
│  │  • 对应管理面板的一个功能模块                          │   │
│  │  • 示例：IdentityService、LogService               │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  ExtensionPoint 接口（运行时能力替换）                 │   │
│  │  • 多实现竞争，通过 ExtensionRegistry 注册            │   │
│  │  • 优先级仲裁，支持热替换                              │   │
│  │  • 对应一种可替换的运行时能力                          │   │
│  │  • 示例：AuthProvider、StorageProvider                │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**判别规则：**

| 维度 | 使用 Service 接口 | 使用 ExtensionPoint |
|------|------------------|---------------------|
| 实现数量 | 全局唯一实现 | 可同时存在多个实现 |
| 替换方式 | 整体替换（如换数据库） | 按优先级选择或责任链 |
| 管理界面 | 有对应 CRUD 管理页 | 通常无独立管理页 |
| 默认行为 | 必须有默认实现（开箱即用） | 可为空（插件提供） |
| 热替换 | 通常需重启 | 支持运行时热替换 |

### 二、Service 接口体系设计

**CRUD 方法命名统一规范**：所有单一实体（单对象）的 Service 接口，其 CRUD 方法名统一采用简短形式，与现有 `UserService`、`RoleService` 保持一致：

| 操作 | 方法名 | 返回类型 | API 端点（Controller） |
|------|--------|---------|----------------------|
| 分页列表 | `list(int page, int size)` | `PageResult<T>` | `GET /admin/v1/{resource}` |
| 获取详情 | `get(String id)` | `Optional<T>` | `GET /admin/v1/{resource}/{id}` |
| 创建 | `create(T entity)` | `T` | `POST /admin/v1/{resource}` |
| 更新 | `update(String id, T entity)` | `T` | `PUT /admin/v1/{resource}/{id}` |
| 删除 | `delete(String id)` | `void` | `DELETE /admin/v1/{resource}/{id}` |

> 注：`IdentityService` 为聚合接口（合并用户+角色+权限），需使用实体前缀命名（如 `listUsers`、`getUser`）以区分不同实体，不适用上述简短规范。

#### 2.1 平台 Service 接口全景

```
api/service/
├── IdentityService          ← 统一身份管理（用户+角色+权限）
├── DictionaryService        ← 字典管理

```

#### 2.2 IdentityService（用户-角色-权限统一管理）

**定位**：聚合用户、角色、权限的管理面板 CRUD 能力，作为不可分割的统一替换单元。

**设计理由**：
- 用户-角色-权限三者存在强关联（用户拥有角色、角色包含权限），分开替换必然导致数据不一致
- 管理面板的用户列表、角色列表、权限树属于同一个功能模块，没有分开替换的业务场景
- 参考 Spring Security 的 `UserDetailsManager` 模式——一个接口统一管理用户与权限

```java
package com.nexusadmin.api.service;

import com.nexusadmin.api.domain.identity.Permission;
import com.nexusadmin.api.domain.identity.Role;
import com.nexusadmin.api.domain.identity.User;
import com.nexusadmin.api.domain.result.PageResult;

import java.util.List;
import java.util.Optional;
import java.util.Set;

/**
 * 统一身份管理接口，聚合用户、角色、权限的查询与管理能力。
 *
 * <p>管理面板的身份管理界面通过此接口获取数据。平台提供 InMemoryIdentityService
 * 作为默认内存实现（预置 admin 用户），插件可通过声明 IdentityService 类型的 Bean
 * 整体替换为数据库实现。</p>
 *
 * <p><strong>命名说明：</strong>由于本接口聚合了用户、角色、权限三个实体，
 * CRUD 方法使用实体前缀命名（如 listUsers / getUser）以区分不同实体。
 * 单一实体 Service（如 DictionaryService、DepartmentService）则遵循平台统一规范，
 * 使用简短命名（list / get / create / update / delete）。</p>
 *
 * <p><strong>替换语义：</strong>替换此接口意味着同时替换用户、角色、权限三者的底层数据源，
 * 确保关联一致性。不允许部分替换。</p>
 */
public interface IdentityService {

    // ==================== 用户管理 ====================
    PageResult<User> listUsers(int page, int size);
    Optional<User> getUser(String id);
    Optional<User> getUserByUsername(String username);
    User createUser(User user);
    User updateUser(String id, User user);
    void deleteUser(String id);

    // ==================== 角色管理 ====================
    PageResult<Role> listRoles(int page, int size);
    Optional<Role> getRole(String id);
    Set<String> getUserRoleIds(String userId);
    Role createRole(Role role);
    Role updateRole(String id, Role role);
    void deleteRole(String id);

    // ==================== 权限管理 ====================
    List<Permission> listPermissions();
    Set<String> getUserPermissionCodes(String userId);
}
```

**默认实现**：`InMemoryIdentityService`
- 预置 `admin` 用户（拥有 `admin` 角色）
- 预置 `admin` 角色（拥有全部内置权限码）
- 预置 10 个内置权限码：`plugins.view`、`plugins.manage`、`users.view`、`users.manage`、`roles.view`、`roles.manage`、`permissions.view`、`config.view`、`config.manage`、`system.view`

#### 2.5 LogService（日志查看与保留管理）

**定位**：合并原 `LogQueryProvider` ExtensionPoint 和 `LogRetentionPolicy` ExtensionPoint 为一个 Service 接口。

**设计理由**：
- 日志查询本质是管理面板的只读查询接口，只有一个实现（如查询 ES 或数据库），不存在多实现竞争
- 日志保留策略是 `LogService` 的配置属性，不应作为独立 ExtensionPoint
- `LogWriter` ExtensionPoint 保留（写入是运行时能力，可能有多个实现：文件写入 + 网络上报）

```java
package com.nexusadmin.api.service;

import com.nexusadmin.api.domain.log.LogEntry;
import com.nexusadmin.api.domain.log.LogLevel;
import com.nexusadmin.api.domain.log.LogType;
import com.nexusadmin.api.domain.result.PageResult;

import java.time.Instant;
import java.time.Duration;

/**
 * 日志管理接口，提供日志查询、清理与保留策略管理能力。
 *
 * <p>与 LogWriter ExtensionPoint 职责分离：
 * LogWriter 负责"写入"（运行时能力，可多实现），
 * LogService 负责"查询与管理"（管理面板功能，单一实现）。</p>
 */
public interface LogService {

    /** 按条件分页查询日志 */
    PageResult<LogEntry> query(LogType type, LogLevel level, String keyword,
                               Instant from, Instant to, int page, int size);

    /** 获取日志保留策略 */
    LogRetentionConfig getRetentionConfig();

    /** 更新日志保留策略 */
    void updateRetentionConfig(LogRetentionConfig config);

    /** 手动触发日志清理 */
    long cleanupExpired();

    /** 日志保留配置 */
    record LogRetentionConfig(Duration defaultRetention, Duration auditRetention,
                               Duration errorRetention, boolean autoCleanup) {}
}
```

#### 2.6 IPluginStateStore（插件状态持久化）

**定位**：将插件启用/禁用状态的持久化从 `ConfigFacade.setPluginDisabled()` 中抽象为独立接口。

**设计理由**：
- 文件系统始终是插件发现的唯一权威源
- 此接口只存储运行时状态（启用/禁用、操作记录），不替代文件发现
- 默认内存实现从 `disabled.yml` 读取，数据库实现可持久化状态

```java
package com.nexusadmin.api.service;

import java.time.Instant;
import java.util.List;
import java.util.Optional;

/**
 * 插件状态持久化接口，用于跨重启保持插件的运行时状态。
 *
 * <p><strong>设计原则：</strong>文件系统始终是插件发现的唯一权威源。
 * 此接口只存储运行时状态（启用/禁用、操作记录），不替代文件发现。</p>
 */
public interface IPluginStateStore {

    Optional<PluginStateRecord> getState(String pluginId);
    void saveState(PluginStateRecord record);
    void deleteState(String pluginId);
    List<PluginStateRecord> listAll();

    record PluginStateRecord(String pluginId, boolean enabled, String disabledReason,
                              Instant lastOperationTime, String lastOperator) {}
}
```

#### 3.2 AI 扩展点体系重新设计：三层抽象

##### 3.2.1 设计目标

AI 能力不应仅仅是"调用外部 LLM"，而应成为平台原生的一等能力。平台以 **Spring AI** 为 AI 基础设施，融入 Spring 生态：

1. **AI 辅助管理**：AI 能够操作平台（管理插件、查询系统状态、读写配置等），用户通过自然语言与平台交互。基于 Spring AI 的 `ChatClient` + `ToolCallback` 实现
2. **AI 能力可替换**：底层 AI 服务（OpenAI、Ollama、Azure OpenAI 等）通过 Spring AI 的 `ChatModel` 抽象可插拔替换。`AiProvider` 扩展 `ChatModel`，纳入平台 ExtensionPoint 体系
3. **平台作为 MCP 服务端**：通过 `spring-ai-starter-mcp-server` 原生实现 MCP 协议，可被 Claude Desktop、Cline、VS Code Copilot 等外部 AI 工具直接调用。插件贡献的 `AiSkill`（扩展 `ToolCallback`）自动暴露为 MCP 工具
4. **能力可拓展**：技能（`AiSkill extends ToolCallback`）、知识源（`AiKnowledgeSource`）可独立拓展，无需修改核心接口
5. **融入 Spring AI 生态**：上层抽象直接对接 Spring AI 的标准接口（`ChatModel`、`ToolCallback`、`VectorStore`），避免重复造轮，开发者使用 Spring AI 通用 API 即可操作平台 AI 能力

##### 3.2.3 AiProvider（第一层：extends ChatModel）

`AiProvider` 直接扩展 Spring AI 的 `ChatModel` 接口，同时作为平台 ExtensionPoint，融入 Spring AI 生态：

```java
package com.nexusadmin.api.extension.ai;

import org.springframework.ai.chat.model.ChatModel;
import org.springframework.ai.chat.model.ChatResponse;
import org.springframework.ai.chat.prompt.Prompt;
import com.nexusadmin.core.extension.ExtensionPoint;

/**
 * AI 服务提供者扩展点，扩展 Spring AI ChatModel，纳入平台拓展点体系。
 *
 * <p>继承 Spring AI {@link ChatModel} 的全部能力（call、stream），
 * 同时作为平台 ExtensionPoint，支持多实现竞争和运行时热替换。</p>
 *
 * <p><strong>与 Spring AI 生态的关系：</strong>
 * <ul>
 *   <li>任何 Spring AI ChatModel 实现（OpenAI、Ollama、Azure OpenAI 等）
 *       只需额外实现 {@link ExtensionPoint}，即可注册为 AiProvider</li>
 *   <li>Spring AI 的 {@link org.springframework.ai.chat.client.ChatClient}
 *       可直接包装 AiProvider 进行对话</li>
 *   <li>平台通过 ExtensionConsumer&lt;AiProvider&gt; 动态获取最高优先级实现</li>
 * </ul>
 *
 * <p><strong>插件实现示例：</strong>
 * <pre>{@code
 * public class OllamaAiProvider implements AiProvider {
 *     private final OllamaChatModel chatModel;
 *     // 委托所有 ChatModel 方法给 chatModel
 *     public ChatResponse call(Prompt prompt) { return chatModel.call(prompt); }
 *     // ...
 * }}</pre>
 */
public interface AiProvider extends ChatModel, ExtensionPoint {

    /**
     * 获取此 AI 提供者的元信息。
     */
    AiProviderInfo getInfo();

    /** AI 提供者元信息 */
    record AiProviderInfo(String name, String model, String version) {}
}
```

**关键设计点**：
- `AiProvider` **IS-A** `ChatModel`——平台无需自建对话抽象，完全复用 Spring AI 的标准 API（`Prompt`、`ChatResponse`、`Message` 等）
- 插件实现 `AiProvider` 即同时成为 Spring AI `ChatModel` 实现，可被 Spring AI `ChatClient` 直接使用
- 平台通过 `ExtensionConsumer<AiProvider>` 获取最高优先级的 AI 提供者，实现多模型竞争与热替换
- Spring AI 已提供 10+ 种 `ChatModel` 实现（OpenAI、Ollama、Azure、Vertex AI、Bedrock、Anthropic 等），平台开箱即用

##### 3.2.4 AiSkill（第二层：extends ToolCallback）

`AiSkill` 扩展 Spring AI 的 `ToolCallback` 接口，为平台添加 `InvocationContext` 感知和结构化的 `SkillResult` 返回：

```java
package com.nexusadmin.api.extension.ai;

import com.nexusadmin.api.context.InvocationContext;
import org.springframework.ai.tool.ToolCallback;
import org.springframework.ai.tool.definition.ToolDefinition;

/**
 * AI 技能接口，扩展 Spring AI ToolCallback，融入平台 InvocationContext。
 *
 * <p>技能是平台暴露给 AI 的"函数"——AI 理解技能的描述和参数 Schema，
 * 在对话中决定调用哪个技能来完成用户意图。</p>
 *
 * <p>继承 Spring AI {@link ToolCallback}，自动被 Spring AI ChatClient
 * 和 MCP Server 识别为可调用工具。</p>
 *
 * <p><strong>平台内建技能示例：</strong>
 * <ul>
 *   <li>plugin.list — 列出所有插件</li>
 *   <li>plugin.start — 启动指定插件</li>
 *   <li>plugin.stop — 停止指定插件</li>
 *   <li>system.status — 获取系统运行状态</li>
 *   <li>config.get — 读取配置</li>
 *   <li>config.update — 更新配置</li>
 *   <li>log.query — 查询日志</li>
 * </ul>
 *
 * <p><strong>插件可注册自定义技能：</strong>如数据分析插件可注册
 * "analytics.report" 技能，供 AI 在对话中调用。插件声明为 Spring Bean
 * 即可被自动发现。</p>
 */
public interface AiSkill extends ToolCallback {

    /** 技能名称（全局唯一标识），如 "plugin.list" */
    String name();

    /** 技能描述（供 AI 理解何时调用） */
    String description();

    /** 参数 JSON Schema（Draft 2020-12），供 AI 理解参数格式 */
    Map<String, Object> parametersSchema();

    /** 执行技能（平台扩展：携带 InvocationContext） */
    SkillResult execute(Map<String, Object> arguments, InvocationContext context);

    // ===== 桥接到 ToolCallback =====

    /** 将平台级元数据桥接为 Spring AI ToolDefinition */
    @Override
    default ToolDefinition getToolDefinition() {
        return ToolDefinition.builder()
                .name(name())
                .description(description())
                .inputSchema(parametersSchema())
                .build();
    }

    /** 将 Spring AI 的调用桥接到平台 execute()，从 ThreadLocal 获取 InvocationContext */
    @Override
    default String call(String toolInput) {
        Map<String, Object> args = parseJsonToMap(toolInput);
        InvocationContext ctx = InvocationContext.current();
        SkillResult result = execute(args, ctx);
        return toJson(result);
    }

    /** 技能执行结果 */
    record SkillResult(boolean success, String message, Object data) {}
}
```

**关键设计点**：
- `AiSkill` **IS-A** `ToolCallback`——Spring AI 的 `ChatClient` 和 MCP Server 自动识别
- `getToolDefinition()` 桥接：将 `name()` + `description()` + `parametersSchema()` 映射为 Spring AI 的 `ToolDefinition`
- `call(String)` 桥接：从 `ThreadLocal` 获取 `InvocationContext`，委托 `execute()`
- `parametersSchema()` 使用 JSON Schema Draft 2020-12，与平台配置 Schema 体系统一
- 插件只需声明 `AiSkill` 为 Spring Bean 即可被自动发现；运行时也可通过 `AiSkillRegistry.register()` 动态注册

##### 3.2.5 AiSkillRegistry（技能注册表，聚合 Spring Bean + 运行时注册）

`AiSkillRegistry` 是技能的唯一权威来源，聚合 Spring 管理的 `AiSkill` Bean 和运行时动态注册的技能：

```java
package com.nexusadmin.api.extension.ai;

import java.util.List;

/**
 * AI 技能注册表，聚合 Spring Bean 发现与运行时注册，作为技能的唯一权威来源。
 *
 * <p>Spring AI 的 ChatClient 和 MCP Server 通过此注册表获取所有可用工具。
 * Spring 管理的 AiSkill Bean 由 {@code DefaultAiSkillRegistry} 自动收集，
 * 插件也可在运行时调用 {@link #register(AiSkill)} 动态注册。</p>
 */
public interface AiSkillRegistry {

    /** 注册技能（运行时动态注册，用于非 Spring Bean 场景） */
    void register(AiSkill skill);

    /** 注销技能 */
    void unregister(String skillName);

    /** 获取所有已注册技能（聚合 Spring Bean + 运行时注册，去重） */
    List<AiSkill> listAll();

    /** 按名称查找技能 */
    AiSkill get(String skillName);
}
```

**与 Spring AI 的协作关系**：
- `DefaultAiSkillRegistry` 实现通过 `@Autowired List<AiSkill>` 自动收集所有 Spring Bean，同时维护运行时注册的 `ConcurrentHashMap`
- Spring AI 的 `ChatClient` 可直接使用 `AiSkillRegistry.listAll()` 作为工具列表
- MCP Server 的 `tools/list` 和 `tools/call` 委托给 `AiSkillRegistry`
- 这类似于 Web 接入机制中 `PluginWebRegistry` 的角色——聚合 Spring 发现和运行时注册

##### 3.2.6 AiKnowledgeSource（第三层：AI 知识源）

```java
package com.nexusadmin.api.extension.ai;

import com.nexusadmin.api.context.InvocationContext;
import com.nexusadmin.core.extension.ExtensionPoint;

/**
 * AI 知识源扩展点，提供可被 AI 检索的领域知识。

 * <p>知识源为 AI 提供"背景信息"——平台文档、数据库 Schema、

public interface AiKnowledgeSource extends ExtensionPoint {

    /**
     * 按查询条件检索知识。

     * @param query   自然语言查询

     * @param context 调用上下文

    List<KnowledgeEntry> search(String query, int topK, InvocationContext context);
```

##### 3.2.7 平台作为 MCP 服务端（spring-ai-starter-mcp-server）

平台通过 **`spring-ai-starter-mcp-server`** 原生实现 MCP 协议，无需自建适配层。`AiSkill` 因扩展 `ToolCallback`，被 Spring AI MCP Server 自动发现并暴露为 MCP Tool：

**MCP 协议与平台抽象的映射关系（基于 Spring AI 自动桥接）：**

```
MCP 协议概念               Spring AI 抽象              平台抽象
─────────────────────────────────────────────────────────────────
Tool (工具)             ←  ToolCallback            ←  AiSkill
  ├─ tools/list         ←  自动扫描 ToolCallback Bean  ←  AiSkillRegistry.listAll()
  └─ tools/call         ←  ToolCallback.call()      ←  AiSkill.execute()

Resource (资源)         ←  —（自定义适配）            ←  AiKnowledgeSource
  ├─ resources/list     ←                           ←  ExtensionConsumer<AiKnowledgeSource>
  └─ resources/read     ←                           ←  AiKnowledgeSource.search()
```

**MCP Server 启动流程（全部由 Spring AI 自动完成）：**

```
启动阶段：
  spring-ai-starter-mcp-server 自动配置
      │
      │ 扫描所有 ToolCallback Bean（含所有 AiSkill Bean）
      ▼
  自动生成 tools/list 响应
      │
      │ 扫描所有 @McpTool 注解方法
      ▼
  全部工具自动可用

运行阶段：
  外部 AI 工具（Claude Desktop / Cline / VS Code 等）
      │
      │  MCP 协议连接（stdio / SSE / Streamable HTTP）
      ▼
  spring-ai-starter-mcp-server（自动处理 JSON-RPC）
      │
      │  tools/list  → 从 AiSkillRegistry 获取
      │  tools/call  → 委托 ToolCallback.call()（即 AiSkill.call()）
      ▼
  AiSkillRegistry（聚合 Spring Bean + 运行时注册）
```

**插件如何贡献 MCP 工具（两种方式，与 Web 接入机制对等）：**

| 贡献方式 | 机制 | MCP 效果 |
|---------|------|---------|
| 声明 `AiSkill` 为 Spring Bean | `@Bean` 或 `@Component`，Spring AI 自动发现 `ToolCallback` | 自动出现在 `tools/list` |
| 运行时注入 `AiSkillRegistry.register()` | 插件在 `onInit()` 中动态注册 | 同上，无需 Spring Bean |
| 实现 `AiKnowledgeSource`（ExtensionPoint） | 由 `ExtensionRegistry` 自动发现 | 出现在 `resources/list`（需平台实现资源适配器） |

**Spring Boot 配置示例**：

```yaml
# application.yml
spring:
  ai:
    mcp:
      server:
        name: nexus-admin
        version: 1.0.0
        type: SYNC
        protocol: STREAMABLE  # 或 SSE / STDIO
```

**关键设计点：**
- 平台**不**自建 MCP 端点——完全依赖 `spring-ai-starter-mcp-server` 的自动配置，MCP JSON-RPC 处理、传输层、协议版本等全部由 Spring AI 负责
- `AiSkill extends ToolCallback` 是无缝集成的关键：Spring AI MCP Server 自动扫描所有 `ToolCallback` Bean，无需额外适配代码
- `AiSkillRegistry` 是工具的唯一权威来源，MCP Server 的工具解析委托给 `AiSkillRegistry`，确保 Spring Bean 和运行时注册的技能都被纳入
- 插件贡献 MCP 工具的体验与 Web 端点完全对等：声明 Bean 即自动暴露，无需关心底层协议细节
- MCP 资源（resources）的适配由平台在 `McpAutoConfig` 中实现，将 `AiKnowledgeSource` 桥接为 MCP Resource

### 五、Core Facade 接口化

#### 5.1 现状问题

Core 的四个 Facade 均为具体类：

```java
// 当前：AbstractPluginManager 依赖具体类
protected final PluginFacade pluginFacade;
protected final ExtensionFacade extensionFacade;
protected final ConfigFacade configFacade;
protected final EventBusFacade eventBusFacade;
```

问题：
- 具体类形态使得框架适配（如 Spring Bean 替换）只能通过包装而非接口替换实现
- `app` 模块适配 Spring 时只能通过 `@Bean` 覆盖整个 Facade 实例
- 测试时无法简单 mock

但 Core 内部已有良好的接口抽象：`PluginRegistry`、`EventBus`、`ExtensionRegistry`、`ConfigManager` 等核心组件本身就是接口。Facade 本质是这些核心接口的聚合入口，其具体类形态并非阻塞问题。

#### 5.2 决策：Facade 接口化时接口必须留在 core 模块

**核心约束**：Core 模块将来可能作为独立的 Maven 依赖发布，必须保证自身完整可用。因此，Facade 接口化时，接口定义必须保留在 **core 模块内部**（与 `PluginRegistry`、`EventBus` 等接口同级），不能提取到 api 模块。

```
core/facade/
├── IPluginFacade.java        ← 接口（core 模块内）
├── PluginFacade.java         ← 默认实现（core 模块内）
├── IExtensionFacade.java     ← 接口（core 模块内）
├── ExtensionFacade.java      ← 默认实现（core 模块内）
├── IConfigFacade.java        ← 接口（core 模块内）
├── ConfigFacade.java         ← 默认实现（core 模块内）
├── IEventBusFacade.java      ← 接口（core 模块内）
└── EventBusFacade.java       ← 默认实现（core 模块内）
```

**实施时机**：当前阶段暂不执行。原因：

1. Core 内部已有 `PluginRegistry`、`EventBus` 等核心接口提供底层可替换性，Facade 接口化属于锦上添花
2. `AbstractPluginManager` 通过构造函数注入 Facade，app 模块可通过 `@ConditionalOnMissingBean` 覆盖整个 Facade 实例
3. 当前 Facade 的方法签名与底层核心接口高度一致，接口化的直接收益有限

**远期方向**（不纳入当前实施，但必须遵循此约束）：
- 若未来需要支持多框架适配（如从 Spring 迁移到 Quarkus），在 core 模块内将 Facade 转为接口
- `app` 模块的 `@ConditionalOnMissingBean` 和 `PluginRuntime` 模式当前已提供充分的可替换性
- 即使将来接口化，**接口定义绝不离开 core 模块**，以保持 core 作为独立依赖的完整性

### 六、Controller 层重新规划

**REST API 统一规范**：所有 CRUD Controller 遵循与现有 `UserController`、`RoleController` 一致的 REST 端点格式：

| 操作 | HTTP 方法 | URL 路径 | Controller 方法名 |

### 七、AutoConfig 装配体系重构

#### 7.1 新增配置类

新增 `IdentityAutoConfig` 配置类，负责装配身份管理体系：

```java
@Configuration
public class IdentityAutoConfig {

    @Bean
    @ConditionalOnMissingBean(IdentityService.class)
    public IdentityService identityService() {
        return new InMemoryIdentityService();
    }

    @Bean
    @ConditionalOnMissingBean(DefaultPermissionResolver.class)
    public DefaultPermissionResolver defaultPermissionResolver(
            IdentityService identityService,
            ExtensionRegistry extensionRegistry) {
        DefaultPermissionResolver resolver = new DefaultPermissionResolver(identityService);
        extensionRegistry.register(PermissionResolver.class, resolver, 25);
        return resolver;
    }

    @Bean
    @ConditionalOnMissingBean(PluginStateStore.class)
    public PluginStateStore pluginStateStore() {
        return new InMemoryPluginStateStore();
    }
}
```

## 总结

### 核心决策一览

| 决策项 | 结论 | 关键依据 |
|-------|------|---------|
| 接口分类体系 | Service（单一实现，CRUD）vs ExtensionPoint（多实现，运行时） | 替换粒度不同，使用场景不同 |
| CRUD 命名规范 | 单一实体 Service 方法统一为 list/get/create/update/delete；Controller 端点统一为 GET/POST/PUT/DELETE | 不同对象使用相同格式，降低学习成本 |
| 身份管理统一 | IdentityService 聚合用户+角色+权限 | 三者不可分割替换 |
| AI 扩展点重构 | 融入 Spring AI 生态：AiProvider（extends ChatModel）+ AiSkill（extends ToolCallback）+ AiKnowledgeSource；MCP Server 由 spring-ai-starter-mcp-server 原生提供 | 平台原生AI能力融入Spring生态，复用Spring AI全部provider；插件贡献Tool自动暴露为MCP工具 |
| 日志接口重构 | LogQuery + Retention → LogService | 查询是非多实现的管理面板功能 |
| 路由接口删除 | 删除 RoutingPolicy | 与 Spring MVC 重叠 |
| 插件状态存储 | PluginStateStore 独立接口 | 文件为权威源，数据库为持久化 |
| Core Facade | 暂不接口化；将来接口化时接口必须留在 core 模块 | Core 作为独立 Maven 依赖必须自身完整 |
| 管理面板 Controller | 13 个 Controller 全覆盖 | 每个管理功能都有对应 API |

### 长期演进方向

1. **数据源抽象**：当 `InMemoryIdentityService` 不能满足需求时，可通过实现 `IdentityService` 接入 MySQL/PostgreSQL/LDAP 等
2. **权限模型扩展**：`PermissionResolver` 扩展点支持接入 OPA、Casbin 等外部策略引擎
3. **通知体系**：`NotificationService` 在基础设施就绪后实施
4. **Facade 接口化**：当需要多框架适配时，在 core 模块内将 Facade 转为接口（接口不离开 core）
5. **插件市场**：`IPluginSource` 扩展支持从远程仓库发现和安装插件
6. **AI 与 MCP 能力深化**：平台内建 Skills 逐步完善（配置管理、诊断分析等）；AiKnowledgeSource 接入平台文档和 API 契约；插件可通过 AiSkill / AiKnowledgeSource 贡献自定义 MCP 工具与资源
