# 日志系统

------

## 1. 概述

### 1.1 设计目标

日志系统是 Nexus Admin 平台的基础设施，为平台和插件提供统一的日志写入、存储、查询与管理能力。其设计目标包括：

- **框架无缝桥接**：通过 Logback Appender 自动拦截所有 SLF4J 日志，开发者无需改变 `log.info()` 使用习惯
- **写入与存储解耦**：LogWriter（怎么写）、LogStorage（怎么存怎么查）、LogService（怎么管）三层职责清晰分离
- **类型体系可扩展**：LogType 采用 class 设计（参照 EventScope 模式），插件可通过 `LogType.of()` 零成本创建自定义日志类型
- **可扩展可替换**：LogWriter 作为 ExtensionPoint 支持插件扩展（如转发到 ELK/Loki/Kafka）；LogStorage 支持替换后端（如 ES/数据库）
- **管理面板透明**：LogController/LogService 不感知底层存储实现，统一通过 LogStorage 接口查询
- **上下文自动注入**：通过 SLF4J MDC 机制，将 traceId、userId、tenantId 等上下文信息自动注入日志条目

### 1.2 核心原则

- **SPI 扩展**：LogWriter 通过 ExtensionPoint 暴露，插件可提供自定义日志输出实现
- **框架零侵入**：通过 Logback Appender 桥接，不修改 SLF4J API，开发者无感知
- **职责单一**：LogWriter（写入契约）、LogStorage（存储契约）、LogService（管理门面）三者独立
- **默认可用**：提供 LogbackLogWriter + InMemoryLogStorage 全套默认实现，引入即用
- **管理解耦**：LogController 仅依赖 LogService，不感知底层存储

### 2.2 数据流

```
路径一（隐式——框架日志自动汇入）：
  SLF4J log.info() → Logback 引擎 → LogbackLogWriter.append() → LogStorage.store()

路径二（显式——插件结构化写入）：
  插件代码 → LogWriter.write(LogEntry, context) → LogbackLogWriter → LogStorage.store()

路径三（查询管理——管理面板）：
  LogController → LogService.query() / cleanupExpired() → LogStorage.query() / removeBefore()
```

三条路径最终都汇入同一 LogStorage 实例，保证数据一致性。

### 2.3 三层职责与交互

| 层次 | 接口 | 类型 | 职责 | 可替换性 |
|------|------|------|------|---------|
| 写入层 | `LogWriter` | ExtensionPoint | 定义日志写入契约，插件可实现自定义输出通道 | 多实现竞争，`@Extension` 注解注册 |
| 存储层 | `LogStorage` | 普通接口（非 SPI） | 定义日志存取契约（store/query/removeBefore/count） | Spring `@ConditionalOnMissingBean` 替换 |
| 管理层 | `LogService` | 门面接口 | 封装保留策略、清理调度、统计聚合等管理层逻辑 | 同上 |

## 3. 核心接口定义

### 3.1 LogWriter — 写入扩展点

```java
public interface LogWriter extends ExtensionPoint {
    void write(LogEntry entry, InvocationContext context);
}
```

`LogWriter` 是 ExtensionPoint 子类型，定义结构化日志的写入契约。默认实现 `LogbackLogWriter`（50 优先级），插件可通过 `@Extension(points = LogWriter.class)` 提供高优先级实现覆盖。

### 3.2 LogStorage — 存储抽象

```java
public interface LogStorage {
    void store(LogEntry entry);
    PageResult<LogEntry> query(String category, String typeName, LogLevel level,
                               String keyword, Instant from, Instant to, int page, int size);
    long removeBefore(Instant timestamp);
    long count();
}
```

`LogStorage` 保持最小化接口（4 个方法），仅定义基础存取能力。保留策略计算、清理调度、统计聚合等管理层逻辑归属 `LogService`。

`category` 和 `typeName` 均为 String 类型，不对日志类型做枚举校验，天然兼容插件通过 `LogType.of()` 创建的自定义类型。默认实现 `InMemoryLogStorage` 基于 `ConcurrentLinkedDeque`，容量上限 10000 条。

### 3.3 LogService — 管理门面

```java
public interface LogService {
    PageResult<LogEntry> query(String category, String typeName, LogLevel level,
                               String keyword, Instant from, Instant to, int page, int size);
    LogRetentionConfig getRetentionConfig();
    void updateRetentionConfig(LogRetentionConfig config);
    long cleanupExpired();

    record LogRetentionConfig(Duration defaultRetention, Duration auditRetention,
                               Duration errorRetention, boolean autoCleanup) {}
}
```

`LogService` 面向管理面板，封装保留策略管理、过期清理等管理层逻辑，内部委托 `LogStorage` 完成查询与数据操作。默认实现 `DefaultLogService` 由 `LogAutoConfig` 装配。

### 3.4 领域模型概览

| 类 | 类型 | 说明 |
|----|------|------|
| `LogEntry` | record | 日志条目，含 id、timestamp、type、level、message 及上下文字段 |
| `LogLevel` | enum | 日志级别：TRACE、DEBUG、INFO、WARN、ERROR |
| `LogType` | final class | 日志分类（详见第 4 章），category + name 二维模型，支持 `LogType.of()` 扩展 |

## 4. LogType 可扩展类型体系

### 4.1 设计动机

LogType 由 enum 重构为 final class（参照 [EventScope](file:///c:/Users/starl/Desktop/1_Project/20260124_插件化业务拓展平台/backend/nexus-admin-core/src/main/java/com/nexusadmin/core/event/EventScope.java) 模式），解决两个结构性问题：

1. **不可扩展**：enum 值编译时固定，插件无法注册自定义日志类型
2. **分类混乱**：旧设计混用子系统维度（AI）、技术维度（TECH）、安全维度（AUDIT）等多维分类标准，枚举值持续膨胀

### 4.2 与 EventScope 模式对标

| 概念 | EventScope | LogType |
|------|-----------|---------|
| 不可变性 | `final class`，构造即 snapshot | 同 |
| 分类轴 | `category`（global/platform/plugin/tenant） | `category`（system/audit） |
| 标识轴 | `identifier`（插件ID/租户ID） | `name`（login/api-request 等） |
| 扩展入口 | `EventScope.custom(cat, id)` | `LogType.of(cat, name)` |
| 内置常量 | `EventScope.global()`, `EventScope.platform()` | `LogType.SYSTEM`, `LogType.AUDIT` |
| JSON 序列化 | 无特殊注解 | `@JsonValue` → `"category/name"` |

### 4.3 分类体系：二维精简模型

仅保留两个主分类（category），涵盖平台全部日志场景：

```
                    LogType
                       │
        ┌──────────────┴──────────────┐
        │                             │
    system                          audit
  （平台运行）                     （安全审计）
        │                             │
   general、plugin-lifecycle、    general、login、
   api-request、config-change、   permission、operation、
   ai-call、…                     插件自定义、…
```

| category | 含义 | 典型 typeName |
|----------|------|-------------|
| `system` | 平台运行日志：插件生命周期、API 请求、配置变更、AI 调用、错误堆栈、所有 SLF4J 默认路径日志 | `general`、`plugin-lifecycle`、`api-request`、`config-change`、`ai-call` |
| `audit`  | 安全审计日志：登录/登出、权限检查、敏感操作留痕 | `general`、`login`、`permission`、`operation` |

**设计原则：**
- **category 极简**（只有 2 个）：消除旧设计中 AI、TECH、LOGIN、API 等枚举值膨胀问题
- **name 自由扩展**：插件通过 `LogType.of("system", "custom-event")` 零成本创建
- **查询接口使用 String**：`LogStorage.query(category, typeName, ...)` 天然兼容任意自定义类型

### 4.4 内置工厂方法

LogType 通过静态常量提供通用类型，通过静态工厂方法提供语义化子类型：

| 获取方式 | 类型 | JSON 序列化 |
|---------|------|------------|
| `LogType.SYSTEM` | 系统通用 | `"system/general"` |
| `LogType.AUDIT` | 审计通用 | `"audit/general"` |
| `LogType.systemPluginLifecycle()` | 插件生命周期 | `"system/plugin-lifecycle"` |
| `LogType.systemApiRequest()` | API 请求 | `"system/api-request"` |
| `LogType.auditLogin()` | 登录事件 | `"audit/login"` |
| `LogType.of("system", "xxx")` | 插件自定义 | `"system/xxx"` |

`LogType.of(category, name)` 是插件扩展的唯一切入点，无额外注册表或注解——LogType 本身即是扩展友好的值对象。

### 4.5 LogFactory 工厂类

平台在 `api/log/factory/` 包下提供 `SystemLogFactory` 和 `AuditLogFactory` 两个静态工厂类，封装常用日志类型的标准属性键常量和语义化构建方法。工厂类仅是对内置常用类型的便捷封装，插件自定义类型可直接使用 `LogEntry.builder()` 构建。

### 4.6 查询接口影响

| 版本 | 参数 | 示例 |
|------|------|------|
| 旧（enum） | `type=SYSTEM` | `GET /admin/v1/logs?type=SYSTEM` |
| 新（class） | `category=audit&typeName=login` | `GET /admin/v1/logs?category=audit&typeName=login` |

筛选能力：

| 场景 | URL |
|------|-----|
| 全部系统日志 | `?category=system` |
| 全部审计日志 | `?category=audit` |
| 登录审计 | `?category=audit&typeName=login` |
| 多条件组合 | `?category=system&typeName=api-request&level=ERROR` |
| 插件自定义 | `?category=system&typeName=order-created` |

## 5. SLF4J 桥接机制

### 5.1 桥接架构

`LogbackLogWriter` 同时实现 `AppenderBase<ILoggingEvent>` 和 `LogWriter`，形成 SLF4J → 平台日志的桥梁：

- **Appender 角色**：在 `start()` 时附加到 Root Logger，拦截所有 SLF4J 日志事件，转换为 `LogEntry` 后写入 `LogStorage`
- **LogWriter 角色**：接收插件或代码显式写入的结构化日志，自动补全 `InvocationContext` 中的上下文信息

两种路径最终都委托同一 `LogStorage` 实例完成存储，保证数据一致性。

与 AI 体系的桥接模式对照：

| 层面 | AI 体系 | 日志体系 |
|------|--------|---------|
| 能力扩展点 | `AiProvider extends ExtensionPoint` | `LogWriter extends ExtensionPoint` |
| 框架桥接 | `ChatLanguageModel` 委托 AiProvider | `LogbackLogWriter` 拦截 SLF4J → 委托 LogWriter |
| 桥接方向 | 平台 → 框架 | 框架 → 平台 |
| 可选装配 | `@ConditionalOnClass("langchain4j")` | Logback 随 Spring Boot 自动装配 |

### 5.2 MDC 上下文注入

平台通过 SLF4J MDC（Mapped Diagnostic Context）将上下文信息注入日志，`LogbackLogWriter` 在 `append()` 时自动提取：

| MDC 键 | 对应 LogEntry 字段 | 注入位置 |
|--------|------------------|---------|
| `traceId` | traceId | AuthFilter，自动生成 UUID |
| `userId` | userId | AuthFilter，认证通过后设置 |
| `tenantId` | tenantId | AuthFilter |
| `channelId` | channelId | AuthFilter（如 "HTTP"） |
| `logType` | type | 业务代码，格式 `"category/name"`，未设置时默认 `LogType.SYSTEM` |

`logType` 键支持动态路由：`MDC.put("logType", "audit/login")` 后，当前线程的所有 SLF4J 日志自动标记为审计登录类型。

## 6. 配置与装配

### 6.1 LogAutoConfig 装配清单

所有 Bean 均带 `@ConditionalOnMissingBean` 保护，支持插件覆盖任意环节：

```
LogAutoConfig
│
├── LogStorage   (default: InMemoryLogStorage)
│     @ConditionalOnMissingBean(LogStorage.class)
│
├── LogWriter    (default: LogbackLogWriter)
│     @ConditionalOnMissingBean(LogWriter.class)
│     注入 LogStorage，start() 时附加到 Root Logger
│
└── LogService   (default: DefaultLogService)
      @ConditionalOnMissingBean(LogService.class)
      注入 LogStorage，封装查询与保留策略管理
```

`ServicesAutoConfig` 将原 `InMemoryLogService` 的 Bean 装配移除，`LogService` 的装配逻辑迁移至 `LogAutoConfig`。

### 6.2 配置属性

```yaml
panel:
  log:
    max-entries: 10000            # 内存存储最大条目数
    auto-cleanup: true            # 是否启用自动清理
    cleanup-cron: "0 0 3 * * ?"   # 自动清理 Cron 表达式
```

## 7. AbstractPlugin 生命周期日志

`AbstractPlugin` 的四个 `final` 回调方法中注入标准化生命周期日志：

| 回调方法 | 级别 | 说明 |
|---------|------|------|
| `onInitialize` | DEBUG | 初始化属于内部细节 |
| `onStart` | INFO | 启动是关键节点 |
| `onStop` | INFO | 停止是关键节点 |
| `onUnload` | DEBUG | 卸载属于内部清理 |

日志定义在 `final` 方法中（不可被子类覆盖），确保所有插件自动获得统一的声明周期日志。Core 模块仅依赖 `org.slf4j:slf4j-api`（纯接口层），不引入 Logback 等具体实现，保持零框架依赖原则。

## 9. 设计约束与实践规范

### 9.1 日志使用规范

- 所有组件通过 `org.slf4j.Logger` 输出日志，禁止直接使用 Logback/Log4j2 API
- 优先使用 Lombok `@Slf4j` 声明 Logger
- 避免在日志中硬编码上下文信息，通过 MDC 注入 traceId/userId/tenantId

### 9.2 LogWriter 实现规范

- 必须实现 `write(LogEntry, InvocationContext)` 方法
- 通过 `@Extension(points = LogWriter.class)` 注册
- 合理设置 `priority`（默认实现 50，覆盖实现 100+）
- 实现应保持线程安全

### 9.3 LogStorage 实现规范

- 必须实现 `store`、`query`、`removeBefore`、`count` 四个方法
- `query` 返回结果按时间戳降序排列（最新的在前）
- `store` 为线程安全操作
- 通过声明 Spring Bean 替换默认内存实现

### 9.4 上下文注入规范

在 Filter/Interceptor 中将上下文写入 MDC，在 `finally` 块中确保清理：

- `traceId`：请求入口生成 UUID
- `userId`：认证通过后设置
- `channelId`：标识调用渠道（如 "HTTP"）
- `logType`：按需设置，用于路由日志分类

详细示例见用户指南【[使用日志系统](../../user-guid/使用日志系统.md)】。

## 10. 总结

日志系统形成以 **LogWriter（写入扩展点）** 为能力入口、**LogStorage（存储抽象）** 为数据枢纽、**LogService（管理门面）** 为管理出口的三层架构。通过 **Logback Appender 桥接**，实现 SLF4J 日志的零侵入自动汇入，与现有 AI 体系的框架桥接模式一致。

**LogType 采用 EventScope 式 class 设计**，category 极简为 `system`/`audit` 两个维度，name 自由扩展，插件通过 `LogType.of()` 零成本创建自定义日志类型，彻底消除 enum 不可扩展的架构瓶颈。

**核心价值：**

1. **框架无缝桥接**：开发者使用 `log.info()` 即自动汇入平台日志，学习成本为零
2. **写入与存储解耦**：LogWriter 和 LogStorage 可独立替换，扩展灵活
3. **类型体系可扩展**：LogType 由 enum 重构为 class（EventScope 模式），`LogType.of()` 开放扩展；查询接口使用 String 参数，任意自定义类型可被管理面板检索
4. **管理面板透明**：LogController → LogService → LogStorage，不感知底层实现
5. **插件可扩展**：LogWriter 作为 ExtensionPoint，支持多实现竞争与运行时替换
6. **全生命周期覆盖**：AbstractPlugin 统一日志 + AuthFilter MDC 注入 + Logback Appender 拦截，形成完整日志数据链
