# 插件系统设计思路说明

## 1. 设计目标与总体原则

本插件系统的设计目标是：

- 支持插件从**安装 → 启用 → 运行 → 停止 → 卸载**的完整生命周期
- 支持后续扩展**插件管理 API**，供前端插件管理面板使用
- 保证核心系统与插件的**强隔离、弱耦合**
- 插件系统本身保持**轻量、基础设施化**，不承载业务复杂度

总体原则如下：

- 插件模块只关注**插件运行机制**，不关心管理形态
- 插件管理能力属于**宿主系统的应用层能力**
- 插件是被管理对象，而不是管理者

------

## 2. 插件生命周期设计

插件系统应明确区分**逻辑生命周期**与**物理生命周期**。

### 2.1 生命周期阶段定义

| 阶段      | 说明                                   |
| --------- | -------------------------------------- |
| INSTALL   | 插件被安装到系统（文件层面存在）       |
| LOAD      | 插件被加载到 JVM（类加载、元数据解析） |
| ENABLE    | 插件被标记为可用                       |
| START     | 插件开始运行，参与系统行为             |
| STOP      | 插件停止运行，但仍在系统中             |
| UNINSTALL | 插件被完全移除（文件 + 内存）          |

### 2.2 生命周期职责划分

- **PluginLoader**
  - 负责插件的加载（LOAD）
  - 负责插件的物理卸载（UNINSTALL）
- **PluginManager**
  - 负责插件状态流转（START / STOP / ENABLE / DISABLE）
  - 负责编排生命周期调用顺序
- **LoadedPlugin**
  - 仅作为插件运行态的载体
  - 不承担管理职责

------

## 3. 插件管理 API 的定位

插件管理 API 的主要用途是：

- 向前端插件管理面板提供接口
- 提供插件的 CRUD 能力
- 控制插件生命周期（启用、停用、卸载等）

该 API **不属于插件系统核心能力**，而属于宿主系统的管理能力。

结论：

> 插件管理 API 不应放在插件模块中。

------

## 4. 是否需要引入数据库

### 4.1 插件管理是否需要持久化

当存在以下需求时，引入数据库是必要的：

- 插件启用/禁用状态需要重启后保持
- 插件的安装信息需要持久化
- 插件有版本、来源、作者等元数据
- 插件管理面板需要查询、筛选、排序

在典型后台管理系统中，上述需求几乎必然存在。

结论：

> 插件管理模块**需要数据库支持**。

------

## 5. 数据库相关能力的归属

### 5.1 不应放入插件模块的原因

数据库、Mapper、Controller 等不应放入插件模块，原因包括：

- 插件模块应保持基础设施属性
- 插件系统不应绑定具体 ORM 技术（如 MyBatis）
- 插件系统可能被不同宿主复用
- 插件模块不应暴露 HTTP 接口

### 5.2 正确的模块划分

推荐的模块结构如下：

```text
project-root
├─ plugin-core            # 插件核心（无数据库、无 Web）
│  ├─ PluginLoader
│  ├─ PluginManager
│  ├─ PluginDescriptor
│  └─ lifecycle
│
├─ plugin-admin            # 插件管理模块
│  ├─ controller           # 插件管理 API
│  ├─ service              # 插件管理服务
│  ├─ mapper               # MyBatis Mapper
│  ├─ entity               # 插件持久化模型
│  └─ converter            # DB ↔ PluginDescriptor
│
└─ application             # 主应用
```

------

## 6. 插件管理模块的职责

### 6.1 plugin-admin 模块职责

- 提供插件管理 REST API
- 持久化插件状态与元数据
- 调用 PluginManager 执行实际操作

其行为特点：

- **只做决策，不做执行**
- **不直接操作 ClassLoader**

### 6.2 plugin-core 模块职责

- 插件加载、启动、停止、卸载
- 插件隔离与安全控制
- 生命周期一致性保障

其行为特点：

- **只执行，不决策**
- **不依赖数据库与 Web**

------

## 7. 插件管理 API 与插件系统的交互方式

典型调用链如下：

```text
前端管理面板
  ↓ HTTP
PluginAdminController
  ↓
PluginAdminService
  ↓
PluginManager（plugin-core）
```

- PluginManager 不感知数据库
- PluginAdminService 不处理底层细节

------

## 8. 插件元数据与运行态分离

推荐区分两种对象：

- **PluginEntity（持久化态）**
  - id
  - version
  - enabled
  - installPath
- **LoadedPlugin（运行态）**
  - classLoader
  - state
  - pluginInstance

二者通过 id 关联，但生命周期不同。

------

## 9. 设计结论总结

- 插件模块本身不引入数据库、不暴露 API
- 插件管理能力通过独立模块实现
- 插件系统只关心生命周期执行
- 插件管理模块负责持久化与前端交互

该设计能够保证：

- 插件系统长期稳定
- 管理能力可演进
- 插件与宿主系统职责清晰

------

## 10. 后续可扩展方向

- 插件权限与安全沙箱
- 插件依赖关系管理
- 插件版本升级与回滚
- 分布式插件管理

以上扩展均不破坏现有模块边界。
