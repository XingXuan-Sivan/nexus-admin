#### 代码质量与架构规范

- **架构原则**：代码须遵循高内聚低耦合原则，确保职责边界清晰，杜绝重复逻辑，以保障系统的优雅性、规范性及可演进能力。
- **注释规范**：保持与现有代码风格一致，仅描述代码意图，严禁包含 `@since`、`@author` 等元数据标签及修改历史记录。
- **API规范**：统一规范Controller与Service层的方法命名及API设计，特别是针对CRUD操作，确保不同对象的增删改查方法命名风格、参数格式与API路径结构保持一致，形成清晰一致的开发约定。
- **配置管理**：横切关注点（如过滤器、拦截器）应基于基路径配置以符合开闭原则；所有通用路径及配置项必须收敛至常量类或配置文件，严禁在代码中硬编码或重复定义。
- **配置抽象化**：配置文件中的业务前缀（如项目名）不应写死，须使用通用化、抽象化的前缀（例如将 `nexus.admin` 调整为 `panel`），以增强配置的复用性和通用性。
- **工具类复用**：通用逻辑必须封装为独立工具类，开发时优先复用现有工具包，严禁在业务代码中重复造轮子。
- **国际化**：系统提示语及日志信息必须使用中文。

#### 交付与文档标准

- **零技术债**：严禁遗留临时代码或未完成的逻辑，确保交付质量。
- **全局清理**：重构或修改完成后，必须执行全局扫描，彻底删除不再使用的旧目录和类文件。
- **文档一致性**：同步更新设计文档与用户文档，确保其内容与代码实现完全一致，严禁编造未实现的设计；同时保持文档整体风格统一。
- **ADR文档**：历史决策记录不可修改，仅依据项目现状及时更新其决策状态。
- **设计文档**：设计文档需聚焦系统顶层架构、核心交互、状态流转、框架性代码等抽象且持久的内容，确保长期有效；仅在发生重大架构调整或系统性变更时更新，避免因日常功能迭代或代码细节变动而频繁修改。如被修改，不应包含历史设计内容。
- **用户文档**：用户文档须随功能变更同步更新，确保描述与产品界面、操作流程及实际行为严格相符，内容准确、清晰易懂。
